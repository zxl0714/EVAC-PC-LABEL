# CAVE PC Collection 实施计划

CAVE PC Collection 将多款 CAVE 游戏整合成一个 Windows x64 工程：用户打开同一个启动器，通过一份 `config.ini` 配置常用选项，只安装自己拥有的游戏数据；开发者从同一个仓库准备工具、编译、测试和打包。

实施顺序为先完成 ESPGaluda II（G2）的可玩基线，以 G2 建立合集，再合入虫姬二，最后合入绊地狱。前三款完成后逐款加入 ESP Ra.De.、怒首领蜂大往生等作品。每一阶段以独立提交和对应验收收尾，逐步推进，不同时改写全部工程。

首个完成上述三款整合与 P6 验收的合集版本定为 **v0.1**，不把当前尚在测试的 G2 单游戏基线提前标成正式 v0.1。怒首领蜂大往生与 ESP Ra.De. 保持 Coming Soon，不作为首版发布的前置条件。

## 产品范围

- 目标平台为 Windows x64。移植程序使用项目维护的独立运行时，不以调用完整 Xenia 或 shadPS4 作为合集的游戏实现。
- 首版启动器提供纵向游戏 banner 列表、安装状态、启动、选择数据目录、打开配置和打开日志目录。先完成启动页视觉方案与效果图，再实现界面；配置采用文本编辑，内置配置编辑器和在线更新不纳入首版。
- 不带任何 ROM 也能打开启动器；只安装一款游戏也能完整使用。
- 显示、音量、键盘、SDL 手柄和社区偏好共用默认配置，各游戏可在同一文件内覆盖。
- 每款游戏的游戏内设置、存档、录像、缓存和日志分别保存。昵称不作为存档目录标识，改昵称不丢进度。
- 游戏在独立子进程运行。首版一次只运行一款，正常退出或崩溃后启动器仍可使用；不做进程内热切换。
- 一套构建入口可选择编译部分或全部已接入游戏，不要求同时提供所有游戏数据。

## 启动页产品与视觉设计

启动页以简洁、优美为主要目标。先调研成熟游戏库与启动器的界面，形成产品布局和视觉方案，制作效果图并自行 review、迭代和定稿，再进入界面开发，不等待用户评审或逐项确认。自审重点包括整体美感、标题可读性、五款游戏的辨识度、状态区分、操作层级与小窗口布局。

页面从上到下排列横幅式游戏 banner，展示顺序固定如下：

| 顺序 | 游戏 | 首版展示 |
| --- | --- | --- |
| 1 | 虫姬二／Mushihimesama Futari | 游戏 banner 与实际安装、可启动状态 |
| 2 | ESPGaluda II | 同上 |
| 3 | 绊地狱／Ketsui | 同上 |
| 4 | 怒首领蜂大往生／DoDonPachi DaiOuJou | Coming Soon |
| 5 | ESP Ra.De. | Coming Soon |

这一顺序只决定首页展示，不改变先 G2、再虫姬二、最后绊地狱的开发与迁移顺序。尚未接入的游戏与“已经支持但缺少数据”分别展示，用户只有部分 ROM 时仍能理解哪些游戏可以启动。

每款游戏的 banner 从网上寻找合适素材，至少清楚呈现游戏标题；保留素材来源与处理说明。允许按视觉需要裁切、修图、叠加标题、遮罩和调整色调，统一横幅比例与整体质感，同时保留各游戏辨识度。优先利用宽画面和留白组织信息，不直接把竖版封面挤压成横图。

大往生和 ESP Ra.De. 保留完整 banner，以降饱和、色调变化或遮罩等方式配合 Coming Soon 标识；具体色彩与构图由效果图阶段决定。未接入项不提供有效的启动动作。效果图同时呈现可启动、缺少数据和 Coming Soon 的区别，并考虑较小窗口下的纵向滚动。

页面提供明确的配置按钮，点击后用文本编辑器打开合集根目录的共用 `config.ini`。不存在时按统一规则创建默认模板，已有配置不覆盖；首版不制作图形化配置页面。启动器与游戏均使用这一份文件，保存后重启游戏生效。

效果图交付包含整体启动页、五款游戏的 banner 选材与状态样式，以及配置入口的位置。布局、配色、字体、留白、悬停和选中效果先以设计方案统一，再选择相应的原生界面实现方式。

调研参考采用 [Playnite 桌面模式](https://api.playnite.link/docs/manual/gettingStarted/playniteDesktopMode.html) 的列表、详情与明确启动动作，以及 [LaunchBox](https://www.launchbox-app.com/) 对游戏画面和标题的组合展示。本合集仅有少量精选作品，设计上保留纵向横幅和直接启动，不引入商店、复杂过滤器或大型侧栏；配置与日志作为页头次要动作。状态文字和操作保持独立可读，不只依赖灰色或彩色区分。

素材候选优先核对各作品官方展示页：[虫姬二](https://www.cave.co.jp/gameonline/Xbox360/mushihime2/)、[ESPGaluda II](https://www.cave.co.jp/gameonline/Xbox360/espgaluda2/)、[绊地狱](https://m2stg.com/ketsui/)、[大往生](https://m2stg.com/daioujou/)、[ESP Ra.De.](https://m2stg.com/esprade/)。最终素材清单记录具体资源地址、版权标注、使用范围与裁切处理，并核对标题和移植版本，避免把虫姬一或最大往生的画面混入。

### 体验一致性

不同游戏共用同一套产品命名和宿主操作约定，而非只统一目录。窗口标题使用固定格式：启动器为 `CAVE PC Collection`，游戏为 `CAVE PC Collection — <游戏显示名>`，例如 `CAVE PC Collection — ESPGaluda II`。游戏显示名来自同一份清单，用于 banner、窗口、启动提示和日志展示；后端名称、SDK 版本及构建标识放在诊断信息中，不作为正常游玩标题的主体。

图标、启动／配置／日志等操作名称、安装状态和错误提示采用共同风格。各游戏的全屏／窗口切换、失焦处理、启动参数和返回启动器的行为保持一致；F11／Alt+Enter 作为宿主全屏切换约定，F8 保留为日志时间标记。游戏内按键仍映射到统一的控制器按钮，不强行把不同作品的特殊玩法改成同一个动作。

迁入每款游戏时，逐项检查标题和图标、窗口／全屏、声音与失焦、共享配置、启动和退出提示、存档／日志入口。宿主可统一的部分抽成公共实现，受后端限制的差异明确记录并验收，不只靠文档约定。

## 工程与运行时边界

共享工程不等于强行共用 GPU 或系统 ABI。合集采用以下分层：

| 层 | 职责 |
| --- | --- |
| 启动器 | 游戏列表、配置入口、安装检测、启动和进程状态；不装载游戏镜像或初始化游戏 GPU |
| 公共组件 | INI、路径、输入配置与按钮定义、日志元数据、文件校验、工具恢复、构建与发布 |
| Xbox 360 运行时 | 一份维护中的 ReXGlue、Xenos/D3D12、XMA/SDL 音频和 Xbox 系统接口，服务虫姬二与 ESPGaluda II |
| PS4 运行时 | 绊地狱现有的装载、系统服务、驻留 GPU、音视频及保存实现；后续适用作品再接入 |
| 游戏适配 | 原始程序身份、模块、函数边界、hook、模式规则、声音线程、保存格式和社区数据映射 |

启动器使用受控的游戏 ID 和清单生成启动参数，不让配置文件指定任意可执行命令。进程启动使用明确的程序路径及正确的参数转义，支持中文、空格和从其他工作目录启动。

最终 Xbox 360 宿主可通过 `--game futari` 或 `--game espgaluda2` 选择相应主程序与 overlay DLL。主程序 DLL 的入口、注册和卸载接口必须先做验证；迁移过渡期可保留分别构建的原生宿主，不为统一 EXE 名字阻塞可玩版本。两款游戏只维护一份 SDK 源码，不永久复制两套兼容实现。

PS4 与 Xbox 360 后端分别链接自己的配套 DLL。即使依赖同名，也不把不同 ABI 或不同构建的文件混放。共用 SDL 的配置和可复用机制，同时保留各后端的初始化线程、焦点和采样约束。

## 游戏数据的放置与检测

游戏 ID 固定为 `futari`、`ketsui`、`espgaluda2`、`esprade` 和 `daioujou`。每款游戏单独定义数据清单，原始目录内部结构保持不变：

| 游戏 | 默认位置与放置方法 |
| --- | --- |
| ESPGaluda II | 完整解包数据放入 `game-data/espgaluda2/`，保留 `default.xex`、模式 XEX 和 `res/DISKDATA` 等原有相对位置 |
| 虫姬二 | 完整解包数据放入 `game-data/futari/`，使 `default.xex` 位于该目录根；DLC 单独放入 `game-data/futari/dlc/`，保留既有内容结构 |
| 绊地狱 | `game-data/ketsui/` 下保留 `CUSA09062-app/` 和 `CUSA09062-patch/` 两层；首期沿用已验证的本体和 1.02 补丁组合 |
| 后续作品 | 接入后给出对应版本和放置说明，不根据名称猜测文件结构 |

启动器的“选择数据目录”只记录路径，不默认移动或改写原文件。另提供显式“复制到合集”操作：目标非空时停止并提示，复制后逐文件校验。数据目录支持外部磁盘，相对路径始终以合集根目录为基准，不以当前工作目录为基准。

游戏清单记录支持的程序版本、必需文件、大小和程序哈希，以及可选 DLC、后端和模块要求。采用分层检测：打开启动器先做轻量存在性检查；准备和首次启动做完整版本校验并缓存结果；关键程序在执行前核验。后台资源检查可以继续进行，但不能把未完成的校验显示为“已验证”。

安装状态区分为“尚未接入”“未安装数据”“数据不完整”“版本不支持”“缺少运行组件”和“可启动”。DLC 缺少只影响对应内容，不把可用的本体整体禁用。首版不执行未知版本，也不自动从网络下载 ROM。

只检查选中游戏所需的数据和组件。一个游戏的坏文件、缺失补丁或离线磁盘不阻塞其他游戏。原始数据挂载只读，准备镜像、资源覆盖、代码生成、工具状态、存档及缓存全部写到数据目录之外。

## 一份 config.ini

根 `config.ini` 是唯一供玩家维护的配置，模板在 `config/default.ini`。不迁入虫姬二旧的首次配置向导，也不让 F4 等调试面板另存一份玩家配置。

以下是待实现的结构示例：

```ini
[collection]
config_version = 1

[display]
fullscreen = false
vsync = true

[audio]
volume = 1.0

[gamepad]
enabled = true
deadzone = 0.20

[keyboard]
up = Up
down = Down
left = Left
right = Right
south = Z
east = X
west = C
north = V
start = Enter
select = Backspace
l1 = A
r1 = S
l2 = Q
r2 = W
l3 = none
r3 = none

[community]
enabled = true
endpoint = https://xiaolu.life/cave/api/v1
nickname = Player

[game.espgaluda2]
data_dir = game-data/espgaluda2

[game.futari]
data_dir = game-data/futari
dlc_dir = game-data/futari/dlc

[game.ketsui]
data_dir = game-data/ketsui
```

公共输入用按钮位置而非游戏动作命名：south 对应 Xbox A／PS4 ×，east 对应 B／○，west 对应 X／□，north 对应 Y／△。投币、换人、觉醒等动作仍由具体游戏的原有按钮设置决定；适配层分别解释 Select、触摸板及其他特殊输入。不能只留下射击和炸弹而丢掉其他可用按钮。

配置优先级为内置默认值、公共配置、当前游戏覆盖、显式命令行临时参数。默认模板不添加游戏级显示、音量或输入覆盖，全部沿用公共设置；有个性化需要时才添加 `[game.<id>.<section>]`。命令行不自动写回配置。游戏相关字段只在选择该游戏时解析，因此某款未安装游戏的错误路径不影响其他游戏。

首次启动只在文件不存在时创建默认配置。以后新增字段通过默认值兼容旧文件，不覆盖个人设置；需要结构迁移时按 config_version 处理，先备份，遇到更新版本则提示而不降级重写。将来启动器编辑配置时使用同一解析器和原子写入，并保留未知字段及注释。无关游戏的覆盖字段错误单独报告，公共配置错误则显示明确的节、键和原因。

公共 endpoint 填写完整的合集 API 根地址，规划为 `https://xiaolu.life/cave/api/v1`，不再增加单独的 uri 配置项，也不需要独立域名。客户端在其后追加 `games/<game>/...`，以游戏 ID 区分榜单和录像。默认昵称为 Player，玩家可自行修改，不使用电脑名。

合集路径在联网整合时部署，目前已有入口为 `/futari/api/v1` 和 `/ketsui/api/v1`。新增合集路径通过分游戏适配保留已有协议和服务，旧入口继续兼容。昵称和联网偏好共享，成绩、录像格式、待传队列及协议版本分别管理；需要独立地址时允许同一 INI 内的游戏级覆盖。未实现联网的游戏显示“暂不支持”，不误连其他游戏的榜单。关闭联网不创建通信工作线程，离线不影响本地游玩。

## 源码与个人数据迁移

G2 可玩基线阶段先在现有 G2 工程继续开发，保留修复前的恢复副本；虫姬二与绊地狱原工程保持不动。从合集工程准备阶段开始，迁移和整合在新合集目录进行，不把原工程就地改成合集。迁入时记录来源仓库、commit、未提交维护改动的摘要和许可证；先审计当前源码快照，再在新仓库建立自己的提交历史。原仓库的既有历史保留供追溯，首版不机械合并三份完整历史，以免把旧生成代码、游戏数据或凭据带入新 Git。

SDK 和提取组件直接维护源码，不建立一套依赖旧目录才能应用的补丁链。第三方子模块与工具使用固定提交或版本及哈希，能从新 clone 恢复。可复用已有下载缓存，但旧机器路径不是必需条件。

个人配置和存档采用显式导入：先预览来源、游戏版本和目标，备份并复制到新的 profile，原文件保持不变。TOML／旧 INI 转换为公共配置和必要的游戏覆盖，无法转换的设置列出，不静默猜测。保存和录像保留原生格式，绝不跨游戏互相转换。

社区待传任务继续携带原游戏、原昵称、原端点和原提交引用。迁移后不能因为使用统一昵称或地址而重绑旧成绩。未识别的旧队列先保留，不猜测关联。运行时对同一游戏 profile 加互斥锁，防止两个进程同时写存档。

## 分阶段实施

### P0 固定迁移基线

优先保存 ESPGaluda II 尚未提交源码的独立恢复副本，记录当前构建、测试 profile 和已知故障；同时只读盘点另外两个项目的维护源码、SDK 差异、依赖锁和已有测试。记录源码来源和输入版本，不复制 ROM、工具安装、派生代码或个人数据到 Git。

先整理 G2 Black Label 选人与录像结束返回的复现步骤；最新回调声明修复标为待实测，不宣告返回崩溃已经解决。虫姬二模式／DLC／声音响应、绊地狱选机与保存／录像先登记为后续迁移对照，不要求先测试另外两款才能继续 G2。

交付物为来源清单、迁移清单、已知问题列表和基线验收表。通过条件是三份原工程和个人文件未被覆盖，未提交维护改动可恢复，待迁入文件已完成源码审计。

### P1 完成 G2 可玩基线

当前先解决 G2 阻塞游玩的帧时间不稳定，再继续其他基线项目。STG 的稳定原作节拍、低延迟输入和音画连续性是进入 P2 的门槛，不属于可以后置的性能细化。以相同录像比较客体出帧间隔、长帧和呈现路径，不能用宿主高 FPS 或提高逻辑速度作为通过依据。

性能优化适可而止：稳定游玩、无频繁长帧后保留回归观测，不为压低单个几毫秒极值持续微调。随后优先补齐 G2 的简化社区／Live，再进行迁移。先确定原版预期，沿用虫姬二仅替换系统通信边界的方式，按 G2 实际数据适配原生榜单、成绩和适用录像；默认昵称 Player，服务使用独立游戏命名空间。G2 先提交成绩再上传录像，不复制虫姬二相反的时序。复用 HTTP 与异步机制；持久化待传和跨重启补传作为 PC 增强项，在原生基本流程之后接入，不当成 G2 原生功能或基本联网的前置条件。断网不影响本地游玩。配置占位、通信单测或只切换登录标志都不算完成。

在现有 G2 工程继续完成移植。优先用已有独立录像复测局末返回，补齐缺失入口的机制回归，再验证至少三次真实进入／返回循环。继续按实际菜单核对七个 overlay 对应的模式，完成可见模式的选人、玩家第一关、死亡复活与适用特殊操作。

验证系统和模式设置保存、局末记录及跨进程读回，完成新录像录制、保存、播放至结束并返回。输入覆盖普通键盘和实体手柄，不以测试用按键延长代替普通输入。音画先检查明显卡顿、秒级延迟和持续积压；需要复用虫姬二调度策略时先确认 G2 调用点，不复制游戏地址。

交付物为可独立运行的 G2 基线、持久源码修复和实际验收矩阵。通过条件是每个可见模式至少一名角色进入玩家第一关，重复进入／返回和保存／录像闭环通过，没有阻塞游玩的已知崩溃或帧时间不稳定。更多角色组合、长期稳定性和不影响游玩的性能细化继续保留，不要求所有边角项完成才建立合集。

### P2 建立合集工程和数据清单

以 P1 的 G2 基线为首个迁移对象，建立目标目录、Git 忽略规则、源码审计、工具版本锁、公共测试入口和版本化游戏清单；在导入本地数据前启用这些边界。实现游戏枚举、路径解析、必需文件检查和状态报告。虫姬二、绊地狱及后续作品先登记，尚未接入的后端明确标记，不要求准备它们的数据。路径校验包含符号链接和目录联接的实际目标，拒绝把准备、日志或存档输出放进原始数据目录。

交付物为可独立构建的基础工程及无窗口检测工具。通过条件是空数据目录、仅一款数据、外部路径、中文空格路径、缺文件、错版本和缺运行组件均能正确区分；测试使用自制数据，不需要 ROM。

### P3 以 G2 接通共享配置和启动器

迁入 G2 的维护 SDK、主程序、七个 overlay、生成声明、诊断和已验证修复，先做到从新合集独立构建。基于现有 G2 INI 接入公共配置、分游戏覆盖、默认配置生成及配置检查，不另造一套长期独立的 G2 平台。

先按“启动页产品与视觉设计”完成调研、素材、效果图与自审定稿，再实现启动器。首版采用 C++ 与 Windows 原生窗口，具体控件和 banner 绘制方式服从自审定稿的视觉方案；独立游戏进程的启动、退出、错误展示与日志目录在此阶段建立。配置按钮直接打开共用 INI，不另做配置界面。启动器的键盘／手柄导航先保留接口，首版以鼠标和键盘选择为验收范围。

启动合同包含游戏 ID、合集根、唯一配置路径、数据／准备目录、profile、日志目录和协议版本。运行时只接受同一份 INI 及解析后的临时值，不要求玩家维护第二份配置。可用自写假游戏进程测试退出和崩溃；不以假进程通过代替真实游戏接入。

通过条件是启动页符合自审定稿的效果图，五款 banner 的标题、顺序和 Coming Soon 状态正确；没有 ROM 也能开列表、选中不可用项能看到具体原因、配置按钮能打开同一份 INI。正常和异常子进程退出均保留启动器，重复启动被阻止，共享默认及游戏覆盖生效。只有 G2 数据时即可由启动器真实选人进入、保存后重启读回并播放录像，复查 P1 的模式切换与声音表现；构建和运行不依赖旧 G2 目录。提供 `CAVE-PC-Collection.exe --game <id>` 直接启动入口和可读 BAT 备用入口。

### P4 接入虫姬二和公共 Xbox 360 运行时

在 P3 已迁入的 G2 SDK 基础上，对照共同基线和虫姬二维护源码逐项合并差异，包括模块分配与卸载、VFS 身份、输入短按、异步日志和诊断。保留双方修复，只维护一份 SDK 源码和依赖锁；导入虫姬二的生成声明及全部模式，迁移旧图形配置为公共 INI。

共用音频后端、局部等待机制和分析工具；声音线程入口、等待调用点、命令队列地址仍属于游戏适配。不得把虫姬二地址直接套到 G2，也不全局取消等待或改变原始音频队列。

通过条件是同一工程可选择单独或同时构建 G2 和虫姬二，使用同一份 SDK，运行时只注册当前游戏的模块；缺少另一款 ROM 不影响本款。虫姬二逐模式实际选人进入、返回及重新进入，本体与 DLC 分别验证保存和重启读取，复查死亡／道具后的音效响应、原有社区和待传。G2 的 P1／P3 流程无退化，两款配置覆盖、存档和缓存互不干扰。公共宿主与分游戏 DLL 的改造单独验证入口和生命周期，过渡期仍可分别构建原生宿主。

### P5 合入绊地狱和 PS4 后端

在双游戏 Xbox 360 平台建立后迁入绊地狱维护源码、驻留图形后端、输入、音视频、保存事务、准备工具和现有回归。保留 PS4 独立运行时，通过既有合集合同接入配置、路径、启动、日志和发布，不改写成 Xbox 360 后端。

先保持后端行为，保留资源读取覆盖与社区整局离线补传，不改原始数据。完成启动全屏接入，并继续单独跟踪已知退出状态、偶发音画卡顿和未完成的模式覆盖。

通过条件是在新工程独立构建并由启动器进入玩家第一关，键盘和 Victrix 方向／按钮可用，真实保存后重启读回，录像保存与跨进程播放；可正常切回启动器。只有绊地狱数据时也能构建和运行，不要求其他游戏 ROM。新增 PS4 后端不影响两款 360 游戏的配置、存档与运行文件。

### P6 完成协作开发和分享包

统一准备、构建、测试和发布入口，清理对旧项目路径的依赖。完成配置／存档显式导入、更新保留、源码审计、构建收据、二进制与 PDB 配对、打包清单及解压校验。源码回归 CI 不需要 ROM；实际游戏检查在本地数据和独立 profile 下进行。

配套文档包括玩家 README.txt、构建开发指南、配置参考、验收矩阵和 FOR_AGENT.md。agent 入口明确目录职责、依赖恢复、生成与编译命令、各后端调试位置、日志／符号定位方法，以及维护源码与生成程序的区别。

v0.1 提供两个固定出包流程，共用同一次已验证构建、版本、配置模板和游戏清单，不维护两套程序实现：

| 包 | 包含内容 | 使用方式 |
| --- | --- | --- |
| 内部完整版 `CAVE-PC-Collection-v0.1-internal.zip` | 启动器、编译后的宿主和游戏模块、必要运行库、一份 config.ini、玩家说明、全部已接入游戏的完整本地 ROM／资源、支持的 DLC／补丁、配套符号，以及完整 `source/.git`、构建脚本和 FOR_AGENT 文档 | 小范围分享，解压即可选择游戏；可在 source 中继续 pull、编译和调试 |
| 对外程序包 `CAVE-PC-Collection-v0.1-public.zip` | 同一套启动器、编译后的宿主和游戏模块、必要运行库、默认 config.ini、数据放置说明、日志提交说明、许可证和第三方声明 | 不含 ROM 和源码；用户自行放入受支持的游戏数据，只拥有一款也可使用 |

内部包的“全部游戏”指该版本已经接入的游戏，v0.1 为虫姬二、ESPGaluda II 和绊地狱，不包含 Coming Soon 项目的未接入 ROM。数据来源由版本清单与显式路径确定，只读复制并逐文件校验；缺少任一应包含游戏的必需数据时停止出包并报告，不静默缩减为不完整的内部包。源码 Git 对象须独立，不引用作者工作目录；源码树与附带程序对应同一发布提交，ROM 不进入源码 Git。

对外包从运行文件白名单独立组装，不先复制内部包再删除文件。禁止包含原始游戏数据、DLC／补丁正文、从 ROM 提取的准备镜像／资源、生成 C++ 正文、维护源码、Git 历史、PDB 或测试现场；空数据目录可以包含放置说明。所需准备内容应由用户本地数据生成，不从内部包带出。已编译的宿主和游戏原生模块属于运行程序，两包使用相同文件哈希。发布前按实际组件核对许可证、第三方声明和对应源码获取要求；对外 ZIP 不内嵌工程源码。

两种包均使用发行默认配置，不附带作者存档、录像、社区待传、日志、缓存、凭据或机器专用绝对路径。出包在全新目录完成，不覆盖旧包和原数据；生成 release.json、文件大小／SHA-256 清单及 ZIP 的 SHA-256。配套完整符号另在本地保留，朋友提交的日志可用版本与 build ID 对应定位。出包脚本只生成本地产物，不自动上传、发消息或发布 Release。

通过条件是在新目录从 clone 恢复工具和依赖、选择单游戏构建并打包；两种 ZIP 在新中文空格目录解压后均能校验和打开启动器。内部包三款游戏均能直接启动，source 的 Git objects 独立，能正常 pull 和增量 build，已有配置及存档不被构建覆盖。对外包先在无数据条件下验证列表和放置提示，再分别以仅一款数据检查启动，不要求补齐其他作品；文件白名单和内容扫描须确认没有 ROM、源码、Git 历史及本地敏感信息。全部发布门槛通过后建立 v0.1 发布标记，不预先把未验收构建标为完成。

首个合集验收还包括上述体验一致性清单、每款游戏的模式切换、真实存档／录像读回、输入与全屏、离线行为，以及至少一次连续 60 分钟的混合游戏流程。切换时退出当前游戏进程，再启动下一款，检查 profile 和缓存隔离。

### P7 逐款增加后续作品

ESP Ra.De. 和怒首领蜂大往生各自先完成数据版本盘点、运行路线与可复用部分评估，再单独制定游戏适配计划。合集只增加清单、适配、生成／准备规则和测试，不复制公共配置、日志或发布系统。每款达到独立游玩和保存标准后，才在启动器标为可玩。

## 构建与发布接口

以下命令为目标接口，在对应阶段实现后同步开发文档：

```powershell
./scripts/Prepare-Tools.ps1 -Profile Build
./scripts/Build.ps1 -LauncherOnly -Jobs 2
./scripts/Build.ps1 -Games espgaluda2 -Jobs 2
./scripts/Build.ps1 -Games espgaluda2,futari -Jobs 2
./scripts/Build.ps1 -Games ketsui -Jobs 2
./scripts/Test.ps1 -Scope Source
./scripts/Release.ps1 -Flavor Internal -Version 0.1
./scripts/Release.ps1 -Flavor Public -Version 0.1
```

启动器、公共库及自造数据测试不要求 ROM。360 游戏原生模块的生成与重建需要对应受支持的数据；显式选择缺少输入的游戏时给出准确错误，不要求另一款游戏数据，也不静默跳过所选目标。从开发包的 source 目录构建时，显式数据参数优先，否则复用包根配置指向的数据，再寻找源码内的默认目录；不要求再复制一份 ROM 到 source，也不把个人 config.ini 当作编译输入。工具区分 Build 与 Reverse 两类，逆向工具不进入玩家启动链。

普通构建默认低优先级、两个编译任务，不自动启动游戏。共同构建入口不要求物理上的单 EXE：发布物包括启动器、所选后端、游戏模块和必要运行文件。发行使用 Release 优化并保留配套符号，记录源码、依赖、配置及输入版本。

发布入口要求明确选择 Internal 或 Public，由同一个打包引擎使用不同内容清单；Public 不接受开启 ROM 或源码的参数。v0.1 内部包固定包含三款已接入游戏，程序包包含对应可运行组件，但构建工具仍保留单游戏选择。两包都不默认包含工具安装、作者测试 profile、缓存或崩溃转储。只读校验不得刷新 Git 索引或改写发行文件。

## 回归与问题处理

公共自动测试覆盖配置继承、路径、数据状态、进程生命周期、日志完整性、版本合同和打包；后端保留各自已有的 ABI、内存、GPU、音频及保存测试。每个真实游玩结果注明构建、模式、角色和测试 profile，当前支持范围写进验收矩阵。

诊断默认启用低开销、有界日志，保留游戏 ID、版本、模块、配置快照、机器信息和配套程序／符号身份。F8 提供时间标记，朋友可从启动器打开对应日志目录并导出一次运行；导出前说明其中包含的昵称和机器信息。细粒度 trace 显式开启，不把逐调用计时常态化。

性能验收比较相同场景的帧时间、长帧和音频队列，区分加载、原作减速和宿主卡顿。迁入前后使用相同配置、存档副本及录像，不用几百 FPS 或调快游戏逻辑代替正确节拍。绊地狱偶发音画停顿、G2 局末返回和虫姬二音效延迟回归分别跟踪，不因合库自动关闭。

启动器使用正常编译、可审计的程序，不加壳、不混淆；保留 BAT 备用入口。若出现杀毒误报，记录具体文件、构建哈希和检测结果并按厂商渠道处理，不要求用户关闭防护或设置排除。原生启动器的误报风险仍需在首包验证，不能保证重新编译即消失。

## 实施顺序与 review 结论

推荐顺序为 P0 固定基线 → P1 完成 G2 可玩基线 → P2 建立合集工程 → P3 以 G2 接通配置和启动器 → P4 合入虫姬二 → P5 合入绊地狱 → P6 统一验收和打包；后续作品在首个合集可交付后逐款推进。首个交付是可玩 G2，首条合集真实闭环也使用 G2，启动器开发不排在 G2 关键修复之前。

G2 与虫姬二使用同一技术路线，先用两款 360 游戏确定公共 SDK 和游戏适配边界，再由绊地狱检验不同后端接入。这样既延续当前 G2 移植，也不要求为了合集先迁移另一套 PS4 平台。

关键收敛点是统一玩家体验和维护入口，而不是先重写 GPU 或强制所有游戏共用一个进程。主程序 DLL 改造单独设验证点；联网整合增加合集路径与兼容分流，保留现有社区服务及协议；全模式回归按游戏分步完成，不让未来两款作品阻塞前三款整合。

P0 源码快照与 P1 的 G2 可玩基线已收尾。用户已完成同进程重复进退，并接受模式设置现有覆盖，不再追加验证；当前推进 P2 合集工程、数据清单和检测，随后接启动器与逐款迁移。实体输入、更多角色和长期稳定性在合集继续回归，正式服务与持久化补传按各自范围实施；阶段状态以 [验收矩阵](TEST_MATRIX.md) 为准。
