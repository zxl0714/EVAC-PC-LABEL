### 音效模块与引擎工作队列

`--sdoj_audio_trace=true` 是默认关闭、启动后不可变的细粒度诊断，不写玩家 INI。源码在 `games/sdoj/diagnostics/audio_*`，声明分为主程序及两套玩法模块；总预算 4096 条，模块观察器只用 try-lock，争用丢弃单独计数。没有改变声音参数、原队列、客体寄存器、原作速度、线程优先级或等待策略，不复制虫姬二的地址与作用域策略。

#### 如何确认是同一份画面

- 模块的 `88031288` 把实际 published 缓冲设给 graphics；+36 虚方法 `88044960` 调用 `880386F0` 解析它。模块 renderer 对象为正常 `885F1A70`、另一布局 `885F97F8`，+900 指向原生绘图列表。这里只读记录原有指针。
- 原生 `8219DC40` 把 `kind=0, draw-list-pointer` 放进 owner+22352 的 8 字节 FIFO；`8219DD38` 放入 `kind=1, frame-end-argument`。成功 store 后的 `8219DCFC`／`8219DDE8` 和成功 pop 返回 `8219DED4` 记录实际 queue／slot／kind／argument。两者不是同一种消息，frame-end 的参数在本场景为零，不能当作绘图列表。

这是宿主键事件到对应输出调用的软件链，不包括实体摇杆／USB、GPU 完成、桌面合成及屏幕扫描／响应。命令语义有自机往返与唯一候选的支持，尚无最终纹理／像素独立认证；不把这两次样本写成全设备、全模式的物理输入延迟。

#### 对上游补丁与下一步的判断

[上游 Input lag 说明](https://github.com/eandis/SDOJ-Recomp#input-lag)将临近消费重采样和提前渲染分开；当前审阅版本为 `cc35e038`，它使用 TU1.01，本项目使用光盘本体。当前合集没有等效的提前渲染修复。之前“同 epoch 掩码生成并复制”只回答了复制前是否新鲜，不能覆盖复制后约 50 ms 的软件链。

优先候选是协调 **提前唤醒玩法／生成命令、在本轮读取前发布、读取新缓冲并跳过重复的后段调用**。现有原顺序中，刚完成的命令等约一帧才发布，发布时本轮 renderer 已读过旧缓冲，又等一轮才用它。把流程前移时，原掩码生成也可能尚未执行，因此要一并处理输入新鲜度，而不是孤立地复制重采样函数。当前按钮到掩码／消费不到 1 ms，单独增加轮询并无已测整帧收益。

最终渲染线程的约一帧等待则是明确的原生节拍点，不应为降低日志数字直接删除、清零或提高游戏速度。先减少其上游的过期缓冲，保留节拍、减速深度、录像输入、存档和模块切换生命周期。预期可削减的帧数属于设计假设，须在后续行为实现后用相同身份链复验，不套用上游 3f→1f 宣称。这轮只做分析和默认关闭的只读探针，未实现行为补丁。

## 虫姬二与最大往生的输入到输出延迟

### 结论与比较口径

虫姬二的原生管线与最大往生不同。已核对的 Ver1.5／Xbox360（`reco_abnormal`）和 Black Label／Xbox360（`kiniro_abnormal`）在普通 depth=1 路径中，通过“唤醒玩法线程 → 等待其完成 → 绘制结果”交接；没有在这些路径发现最大往生已实测的“先读旧 published、后发布新批次、再等下一轮取用”的两轮滞后。玩法线程恢复后还会调用主程序重新取得 XInput 状态，不只是使用主循环早先留下的按钮缓存。

因此，虫姬二具备比当前最大往生更短的游戏内部输入到输出路径；在原生 `1V(Fast)` 路径、工作及时完成时，结构上主要剩一次出帧节拍等待。**这是静态时序判断，不是已经测得合集虫姬二 16.7 ms／一帧，更不是物理摇杆到屏幕出光的数字。** 当前玩家存档的 FrameDelay 值也尚未观察。

| --- | --- | --- |

### 原生 FrameDelay 是必须记录的变量

映像中实际存在 `0V(Tearing)`、`1V(Fast)`、`2V(PCB)`、`3V(Slow)`，由 `821A1DD0` 组成 FrameDelay 的四个选项。该项 ID=3；菜单 setter `8219F790` 经 `8219D218` 写配置对象 `+12`，`82187EE0` 再将此字段写到请求模式 `821F8558`，由帧尾应用。不是只找到几个没有使用的字符串。

原生新建配置与恢复默认均为 **`1V(Fast)`**。`82186B58` 的初始化和 `82186658` 的重置路径都以标志 30 调用 `82185E80`，其中 `82185F04` 将 r28 设为 1，`82185FFC` 将其写到配置 `+12`。这项静态核对说明原生缺省值，不代替当前存档的实际值读回；合集未增加覆盖它的外部 FrameDelay 配置。

这些名称表达原作的呈现选项，不是 PC 软件／物理端到端测量值；特别是 `0V` 不能解释为零延迟。合集共用的 DXGI Present 使用 interval 0，客体等待、GPU 提交和桌面显示合成仍是不同阶段。后续比较应先读回实际 FrameDelay，而非假定玩家一直使用默认值，或直接由 `2V(PCB)` 推出本机恰为两帧。

### 可借鉴的优化方向

优先级与最大往生不同：SDOJ 要先修已证明的跨轮发布／取用；虫姬二应先固定原生 FrameDelay，再量出有效输入消费点到对应图像输出的链路。如果确认只剩一周期内的“过早采样、算完等出帧”，可评估在保持原出帧时刻的前提下，把采样与玩法更新安排得更靠近提交时刻，预留高分位工作时间和安全余量，而不是直接删除等待或提升游戏速度。

独立项目 [futari-nx 的输入延迟研究](https://github.com/ChanseyIsTheBest/futari-nx/blob/main/docs/futari-notes.md#input-lag-2026-10-16-the-users-question-can-we-improve-input-lag-in-the-game-such-as-turning-off-vsync)报告其 PC 录像中首个手柄读取到 Present 约 16.7 ms，通过延后读取降到 5.6–8.2 ms，出帧率不变。这与上述方向相符，但其后端、补丁和测量起点不同，不是本合集的测试结果；其 Switch 显示时钟同步方案也不能直接移植成 Windows 修复。

最小量化补测可只选 1.5 和 Black Label 的短存活自机方向操作，记录实际 FrameDelay、core 输入／命令身份、完成交接、VdSwap 与同图像 Present。复用公共输出来源标签，不把“最近一次 XInput 调用”或“下一次 Present”直接配成因果链。原作 slowdown／录像的语义保留；其余六模块和设备到屏幕的物理测量另列扩展，不为这次结构对照展开全模式游玩。

最大往生的后续工作统一为 [Frame Delay 改进](SDOJ_LATENCY_PLAN.md)：3V 原路径、2V 稳定目标、1V 低延迟目标；借鉴虫姬二的完整结果交接，不照搬其地址、输入缓存或无限等待。具体的行为保持要求、配置设计和验收在方案中集中维护，本项不包含 0V，也不连带改动虫姬二。

本次只增加本地离线分析与文档，没有加入输入、等待或绘图行为补丁，没有启动游戏或改动配置／原始 game-data。以前的 Futari 音频 worker 等待修复不等于输入管线降延迟；目前不能把差异归功于那项修复。

### 地址等待与通知后的长尾

成功等待的恢复路径改为独立 waiter 的原子结果与 Windows `WaitOnAddress`／`WakeByAddressSingle`，不再重新争用共享 semaphore gate。队列次序、完整 credit 预留仍在原 gate 内完成；先建立通知对象的拥有链，再 release 发布结果。等待以 acquire 读取结果，早于停车的通知不会丢失，虚假唤醒继续检查原截止时间。只有超时退休才重新取得 gate，并再次检查是否已获授予；已预留的成功不会被超时覆盖。取消、删除及通知对象生命周期沿用原语义，复用仍有独占所有权和显式发布屏障。依据为 [Microsoft WaitOnAddress 合同](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitonaddress)；不依赖其唤醒顺序实现 guest FIFO。原 CV 路径保留作诊断对照，不改 CPU 映射、电源或优先级。

日志的 `native_semaphore_wait_timing` 现在包含 `wake_began_clock_us`、`wake_finished_clock_us` 和 `address_wait`，可区分发通知之前与之后的延迟。成功可能早于通知调用／结束被观察到，此时相应字段为 0 或通知结束晚于恢复，不作负耗时相加。CV 恢复仍包含重新取 gate；address 的成功路径不包含此步骤。WPR 的 CPU 调度采集因当前非管理员权限未能启动，已核对未在 recording，故没有用内核调度 trace 证明剩余时间全属 Ready 排队。

### 绘图提前提交与排空回调修正

正常路径现在将已记录的绘图指令提前提交，让显卡利用原本的节拍等待时间；最终合成／呈现仍在原显示时钟边界执行。没有更改游戏速度、原作减速、ACQUIRE_MEM 的同步回写、呈现栅栏或 buffer label 的完成条件。同步 Drain 另保留第一次 Finish 和下载回调 FIFO 屏障，但将回调屏障绑定到已提交的 timeline tick，不再为唤醒 CPU 回调额外提交／等待一批空 GPU 指令。普通当前命令回调接口不变；图形自测验证旧回调按序完成且屏障不增加提交或 tick。

`command_stages` 随原有完成帧记录汇总逐次绘制、ACQUIRE_MEM、预取、提前 Flush 及剩余指令处理的宿主耗时。总和及父作用域由分析器校验，父层减内层另列 worker 交接等成本。它不是 GPU timestamp：绘制包含资源／缓存处理，同步排空包含设备和回调等待。新增 `native_semaphore_wait_timing` 记录对象 handle、请求数、排队／授予／恢复时间和最后授予信号的线程及客体调用点；恢复时间包含重新获得 gate，不是纯调度延迟。只记录至少 1 ms 的批量完成等待、至少 2 ms 的授予后恢复或至少 4 ms 的失败等待，每线程每秒最多 8 条，在释放 gate 后格式化。正常单个工作线程待命不刷日志。

- `dropped_oldest`、`contended`、`invalid_records`、`format_failures` 分别记录满队列淘汰、竞争拒绝、无效长度与格式错误。
- `sink_failures` 是后台写入／刷盘失败次数，`sink_wall_max_us` 是本次进程的后台写入最大耗时。
- `pending` 与 `in_flight` 区分排队和正在写入；受控退出先排空队列，再写终止诊断。最后一条状态的 `stop_requested=true`、`drain_completed=true`、两项待写数量为零，表示这次排空完成，不代表此前没有丢弃。

这些值是进程累计状态，选择时间区间后也不重解释成局部计数。旧日志没有这组状态时，完整性仍为未知。新日志中的 `diagnostic_log_us` 和 `previous_frame_log_us` 只计算提交线程的格式化／投递耗时；分析时与后台写入耗时分开。异常强制终止可能来不及排空，锁独立的最后故障记录继续保留；绊地狱退出码 27 的既有限制未因此改变。

独立诊断命令默认保留同步输出。`KetsuiNativeProbe.exe --async-log-self-test` 使用自造阻塞 sink 验证提交与磁盘分离、容量及整条记录、失败计数、多线程投递和排空；`scripts/ps4/run_native_checks.py` 另外检查终止记录仍为最后一条完整 JSON。这些机制检查不执行游戏。

固定录像复测路径为：进入 ARCADE → Backspace 打开暂停菜单 → Materials Room → Replay Theater → My Replay。现有 380 分／TYPE-A／00:53.45 录像可重复用于对照；播放期间不发射击、暂停或加速输入，等待自然返回，再核对 F8、程序哈希、选定区间、丢失状态及音频观测。共享 INI 的临时离线与 CU 方向别名在测试结束后恢复。

## 虫姬二本机联网现场

```powershell
py -3.12 scripts/futari/local_service.py --directory .local/community/futari-check --seconds 1800
```

服务只监听 127.0.0.1 的随机端口，使用原虫姬二协议和全新 SQLite。终端与现场目录的 `service.json` 给出临时 API 根地址；将它临时填入唯一根 INI 的 `[game.futari.community]` 中的 `endpoint`，并显式设置 `enabled = true` 和测试昵称，即可从游戏原生流程验证榜单、成绩及录像。客户端自行追加 `/games/futari`，不把完整游戏路径再填进 endpoint。服务默认 30 分钟后停止，Ctrl+C 可提前结束。

输出必须是合集 `.local` 内不存在的新目录，不复用数据库、不连接正式服务，也不更改服务端默认路由。验证结束后关闭游戏并恢复 INI；保留现场可供只读分析。未完成的待传记录仍属于原服务地址，不能改填正式地址以补传本机测试成绩。
