## 本轮输入延迟结论

范围为虫姬二、G2、最大往生、狱门山、绊地狱和大往生。ESP Ra.De.、弹铳按最新要求暂缓。
软件响应和显示理论分开报告，显示参考统一为 **144 Hz、屏幕中心、固定刷新**。

### 360 统一条件比较

README 和 v0.8.0 更新说明使用以下统一条件估算，取代将单次输入的采样相位直接放进平均延迟横评的做法：

| 游戏 | 移植版延迟/ms | Xenia 延迟/ms | 移植版 CPU/核 | Xenia CPU/核 |
| --- | ---: | ---: | ---: | ---: |
| 虫姬二 | 26 | 36 | 0.08 | 1.26 |
| ESPGaluda II | 26 | 51 | 0.38 | 1.37 |
| 最大往生 | 26 | 69 | 0.43 | 3.46 |

移植版统一使用 1V，G2 为手动启用的实验档，默认仍为 2V；Xenia 分别保留原作 1V／2V／3V。延迟起点是输入状态已到达程序，终点为系统显示事件，不含实体设备／系统输入前段及显示器扫描、面板响应。

统一预算为 `8.33ms 平均采样等待 + 游戏内部响应时间 + 复用的历史呈现后段`。前项假设 60Hz 游戏采样且输入到达相位均匀；不能将最大往生单次约 3ms 的采样等待当作平均值。中项沿用各作已核验的内部链路，移植版约 17ms，Xenia 虫姬二约 16.8ms、G2 约 31.4ms、最大往生约 49.9ms。后项复用虫姬二历史记录的均值：移植版独立翻转 0.919ms、Xenia 桌面合成 11.178ms。表中为这一条件模型的整数毫秒量级，不是各作同次输入到显示的实测均值或尾延迟，也不由几个独立中位数相加构造端到端中位数。

三款移植版共用 `backends/xbox360/host.cpp` 的 Xenos 插件和 `third_party/rexglue/src/ui/d3d12/d3d12_presenter.cpp`，DXGI Present 为 interval 0／RESTART／条件式 ALLOW_TEARING。游戏各自的 V 档位及同步发生在此前，已包含在内部响应时间中，不再重复添加。Xenia 三款也使用同一固定 Canary 构建。共用代码支持建立统一输出条件的比较模型，但不保证每次运行都采用相同的 Windows 翻转／合成路径；窗口状态、驱动和 GPU 负载变化时，历史后段不再是固定附加值。原始后段见[虫姬二历史显示记录](#虫姬二immediate-后仍有显示等待)。

CPU 是同机代表回放的进程执行时间实测，`CPU ms/s / 1000` 为等效逻辑核数，不除以整机 24 个逻辑处理器。虫姬二 77.37／84.21ms/s 两轮取均值后约 0.08 核；最大往生 412.65／456.03ms/s 两轮均值约 0.43 核；G2 使用[最终 1V 组合回归](TEST_MATRIX.md#v080-g2-1v-与性能优化组合)的 380.54ms/s，约 0.38 核，而不是默认 2V 的两轮范围。Xenia 为 1258.97／1373.41／3462.46ms/s，约 1.26／1.37／3.46 核。CPU 场景与输入响应场景分别采样，G2 CPU 为 Black Label／Seseri／No.2，输入响应为 Xbox360／Ageha；这些数字不表示同一局联合采集。原始 CPU 对照见[CPU 对照](#补充优化版与-xenia-的-cpu-对照10月28日)。

### 实体按下到核心：已知路径与理论边界

我们目前使用的是SDL3，不是SDL2。设备扫描／消抖、USB或无线报告、Windows驱动、
输入事件分发，再到游戏采样，是相互独立的环节；没有一个通用的“Windows+SDL延迟”。

| 实现 | 输入更新与读取 | 可作的结论 |
| --- | --- | --- |
| 合集360 | SDL3事件入队，GetState处理已到事件并异步请求UI pump；另有XInput路径。键盘保留尚未被游戏采样的短按 | 正常60Hz、状态到达相位均匀时，仅等游戏读取就可能约0～16.67ms、平均8.33ms；设备和事件分发在此前另计 |
| Xenia固定版本 | SDL2或系统XInput；SDL pump也排往UI线程。原键盘驱动按读取时的当前状态返回 | 不能由SDL版本判断谁固定快几ms；本次1ms级自动短按可落在两次采样之间，不当作人类漏键率 |
| 合集PS4 | SDL3，16.67ms周期采样；数字按下的latch可让ReadReports立即刷新；松开／轴变化不完全走同一路径 | 按下不是必然先额外等一轮采样。应区分数字按下、松开和普通摇杆轴 |
| shadPS4固定版本 | SDL3事件直接更新状态，另有4ms控制器定时轮询；游戏再读报告历史 | 4ms不是所有按钮必加的等待，也不是设备到游戏的上限。大往生本轮实际核心回调约33.39ms，不按配置里的60Hz假定其相位 |

已有真实窗口路径的补充是虫姬二：12次键处理器→首次读取中位7.625ms；8次窗口按下
→首位移Present中位28.859ms。这是键盘事件之后的软件测量，不含触点、USB和OS派发。
Xenia相同工具的12个极短脉冲只观察到1个，不能拿那一例0.0659ms当典型前段或与7.625ms横比。
手柄、摇杆的实体按下前段尚无测量数值。[逐项源码与窗口检查](#输入前段库版本不等于延迟数字)。

### Present到发光与完整总计

144Hz一轮约6.94ms。固定逐行扫描、相位均匀、无额外排队时：即时换图平均等约
3.47ms扫到目标位置；同步换图平均先等3.47ms，再扫约3.47ms到中心，共6.94ms。
VRR、扫描时序和画面位置改变时，模型需随之改变。

完整按下到发光应写成：

`H（实体按下→核心） + B（核心→首响应Present） + R（Present→图像可被显示采用） + S（144Hz中心扫描预算） + D（面板）`

主表实测的是B；上一表给出受控输入的软件前段及直接总计。H、R和D没有完整实测值，
因此本轮不填一个伪精确的物理总延迟。R只计Present之后仍未完成的工作／排队，不重复
计入B内已有的GPU工作和交接。S的3.47／6.94ms也是理想条件均值，不能直接加到CPU
Present上就声称测得出光，更不能将若干独立中位数相加当端到端中位数。
公式描述同一次响应的连续分段；若计算模型平均值，各项也应统一用对应条件的均值。

旧虫姬二同机记录提供了一个实际量级：Present→Windows显示事件中位，合集独立翻转
0.378ms，Xenia桌面合成11.315ms。两边都使用interval0，却有不同后段；这是历史路径
对照，不是当前同一次输入的像素发光数据，也不再叠加一次已包含的刷新等待。
[历史数据与条件模型](#用现有数据先做理论判断)、[144Hz预算假设](#显示器后段的理论预算)。

### 结论与下一步价值

- 虫姬二固定1V，两边软件内部都约17ms；此前降低CPU轮询开销不等于消掉原作的一帧等待。
- G2默认2V与Xenia原作同级，约31～32ms；合集实验1V约17ms，同一合集样本降低约15ms，默认仍为2V。
- 最大往生当前1V相对Xenia原作3V，方向响应少约两个60Hz周期；收益主要来自选择的游戏时序策略。
- 狱门山从API返回到首响应，两边的代表个例均约50ms；核心所属输出之后还要两幅，不能用约17ms内部出图链替代。
- 两款PS4的合集个例均丢弃了首幅响应，下一幅才Present，之后仍有约31／41ms的交接尾段。shad个例直接提交首幅响应。
  后续低延迟工作应优先检查这段图像交接和呈现队列。大往生两边核心回调节拍16.67／33.39ms不同，不能只按一个延迟数给总体体验排名。

所有主行均有像素或明确人工首响应证据；另有同构建图像开／关的交付／呈现控制。
它们没有显示观察器新加一个完整输出周期，不等于零采集开销或全模式验收。
绊地狱合集OFF只作呈现时序对照，不据此确认采样全段存活或OFF首响应。

### PS4 录像结构检查

在已构建的 PS4 运行时上，可只读检查本地压缩附件：

```powershell
./out/ps4-native/KetsuiNativeProbe.exe --community-replay-profile-check daioujou '<本地压缩附件>'
py -3.12 scripts/ps4/run_replay_checks.py
```

第一个命令显式指定标题；可追加原生榜单编号和原生分值整数核对元数据，不猜测另一游戏或版本。第二个命令用自造的不可游玩数据检查两款结构，并将逐项日志及构建身份保存在新的 `.local/ps4-replay-checks/`。结构校验不写入玩家存档、不执行快照，也不代表游戏内回放已通过。

绊地狱沿用 0x80000 字节／1.02 合同；大往生本地存档记录为 0x65600 字节，网络附件内的记录为 0x80000 字节，容器 0x10030、core 0x10000，并接受本体明确附带的 ARCADE_01000／01010／01020／01030 内核。真实测试记录已确认新容器可使用 ARCADE_01000，容器与内核版本不可混为一谈。两者的综合榜编号、角色范围和分值含义不同。大往生代表性原生 loopback 收发、保存及离线冷回放已通过，正式 HTTPS 和正常合集入口仍待验收，当前能力开关保持关闭。

### 原生渲染队列与最终输出：软件链路结论

**当前光盘版保留了约三帧的软件管线延迟，并未因输入掩码新鲜而自动解决。** r7 中 2,216 条完整局部链从玩法读取输入到相应画面的 Present CPU 返回，中位数为 **49.918 ms**、p95 50.327 ms、最大 50.860 ms；全部从 copy 到 VdSwap 跨三个 guest VBlank epoch。首份命令已含方向变化，主要延迟发生在后续发布、取用和原生帧等待，而不是这份玩法更新花了几十毫秒计算。

#### 如何确认是同一份画面

- 模块的 `88031288` 把实际 published 缓冲设给 graphics；+36 虚方法 `88044960` 调用 `880386F0` 解析它。模块 renderer 对象为正常 `885F1A70`、另一布局 `885F97F8`，+900 指向原生绘图列表。这里只读记录原有指针。
- 原生 `8219DC40` 把 `kind=0, draw-list-pointer` 放进 owner+22352 的 8 字节 FIFO；`8219DD38` 放入 `kind=1, frame-end-argument`。成功 store 后的 `8219DCFC`／`8219DDE8` 和成功 pop 返回 `8219DED4` 记录实际 queue／slot／kind／argument。两者不是同一种消息，frame-end 的参数在本场景为零，不能当作绘图列表。
- 原消费线程 `8219CD80` 按顺序执行 kind-0，kind-1 再调用 `8219D148` 结束本帧；此 pop 的序号用宿主 TLS 带到原 `821DFECC` VdSwap 调用前。分析器要求绘图消息和帧结束消息都按实际槽位匹配，绘图列表与模块源记录一致，同一 producer 线程／迭代，且整条来源链中间无缺号。不能只靠相同 host iteration 跨线程匹配。
- 新增默认关闭的 `--output_latency_trace=true`，用 VdSwap 参数转换后的物理 `buffer+28` 匹配 GPU 实际 XE_SWAP 头。专用 GPU-worker 序号随同一输出图像的 mailbox 所有权传到最终 Present。没有往客体命令插标记，没有增加 GPU fence、等待或修改 Present 参数；Present 必须成功且本次提交含客体最终绘图命令。

原生帧结束函数在 `8219D9B0` 将 `8279C770` 置一，循环调用原来的 yield，直到 `8219CCF0` 回调清零；`8219D9C8` 才继续。该回调经初始化设置到 D3D device+16948，由原图形中断路径调用；SDK 的 guest VBlank 会派发图形中断。探针位于置一之前和退出循环之后，不在循环体逐次输出、不清标记。所有 2,216 对等待都跨一个 guest epoch。

#### 对上游补丁与下一步的判断

[上游 Input lag 说明](https://github.com/eandis/SDOJ-Recomp#input-lag)将临近消费重采样和提前渲染分开；当前审阅版本为 `cc35e038`，它使用 TU1.01，本项目使用光盘本体。当前合集没有等效的提前渲染修复。之前“同 epoch 掩码生成并复制”只回答了复制前是否新鲜，不能覆盖复制后约 50 ms 的软件链。

优先候选是协调 **提前唤醒玩法／生成命令、在本轮读取前发布、读取新缓冲并跳过重复的后段调用**。现有原顺序中，刚完成的命令等约一帧才发布，发布时本轮 renderer 已读过旧缓冲，又等一轮才用它。把流程前移时，原掩码生成也可能尚未执行，因此要一并处理输入新鲜度，而不是孤立地复制重采样函数。当前按钮到掩码／消费不到 1 ms，单独增加轮询并无已测整帧收益。

最终渲染线程的约一帧等待则是明确的原生节拍点，不应为降低日志数字直接删除、清零或提高游戏速度。先减少其上游的过期缓冲，保留节拍、减速深度、录像输入、存档和模块切换生命周期。预期可削减的帧数属于设计假设，须在后续行为实现后用相同身份链复验，不套用上游 3f→1f 宣称。这轮只做分析和默认关闭的只读探针，未实现行为补丁。

## 虫姬二与最大往生的输入到输出延迟

### 结论与比较口径

虫姬二的原生管线与最大往生原作 3V 不同。已核对的 Ver1.5／Xbox360（`reco_abnormal`）和 Black Label／Xbox360（`kiniro_abnormal`）在普通 depth=1 路径中，通过“唤醒玩法线程 → 等待其完成 → 绘制结果”交接；没有在这些路径发现最大往生原作已实测的“先读旧 published、后发布新批次、再等下一轮取用”的两轮滞后。玩法线程恢复后还会调用主程序重新取得 XInput 状态，不只是使用主循环早先留下的按钮缓存。

虫姬二原生 `1V(Fast)` 路径主要保留一次出帧节拍等待，后续双方实际测量已确认：Ver1.5 玩法读取到对应 Present 开始中位约 17 ms，测量轮的 FrameDelay 均为 1。最大往生合集默认也已改为 1V；不能沿用早期原作 3V 的结果，声称当前最大往生固定比虫姬二多两帧。两作现有数据的终点／版本不同，详细数字见后面的总表；均不是物理摇杆到面板出光的测量。

| 比较项 | 虫姬二 | 最大往生 |
| --- | --- | --- |
| 公共宿主层 | 与最大往生共用配置输入、SDL 和 D3D12 输出实现 | 同一公共后端 |
| 玩法取输入 | 玩法线程从等待恢复后，经回调重新取得 XInput 状态，再转换玩法输入 | 已实测掩码在同 epoch 内构建并复制；这不消除后段排队 |
| 绘图数据交接 | 主线程等待本次核心交接；生产端先整理绘图数据，再发完成事件，之后绘制 | 原作 3V 晚发布／晚取用；合集 1V 已改为较早交接 |
| 普通节拍 | 代表行固定原生 1V | 合集默认 1V，另可选 2V／3V |
| 已有本机因果链结果 | 当前双方各 60 条输入内容→输出身份配对；合集读取→Present 开始中位 16.984 ms | 历史地图初始化修正版，读取→Present 返回中位：1V 16.847 ms、2V 33.266 ms、3V 49.957 ms |

既有 `.local/llvm23-validation-20261019/futari-new-pacing.json` 的 Black Label 录像有 1,087 个 host_present 间隔，最大 17.477 ms；它说明该段出帧节奏，不能填入上表作为输入延迟。画面可以稳定每 16.7 ms 出一帧，同时仍显示几帧前的输入。

### 原生 FrameDelay 是必须记录的变量

映像中实际存在 `0V(Tearing)`、`1V(Fast)`、`2V(PCB)`、`3V(Slow)`，由 `821A1DD0` 组成 FrameDelay 的四个选项。该项 ID=3；菜单 setter `8219F790` 经 `8219D218` 写配置对象 `+12`，`82187EE0` 再将此字段写到请求模式 `821F8558`，由帧尾应用。不是只找到几个没有使用的字符串。

原生新建配置与恢复默认均为 **`1V(Fast)`**。`82186B58` 的初始化和 `82186658` 的重置路径都以标志 30 调用 `82185E80`，其中 `82185F04` 将 r28 设为 1，`82185FFC` 将其写到配置 `+12`。这项静态核对说明原生缺省值，不代替当前存档的实际值读回；合集未增加覆盖它的外部 FrameDelay 配置。

这些名称表达原作的呈现选项，不是 PC 软件／物理端到端测量值；特别是 `0V` 不能解释为零延迟。合集共用的 DXGI Present 使用 interval 0，客体等待、GPU 提交和桌面显示合成仍是不同阶段。后续比较应先读回实际 FrameDelay，而非假定玩家一直使用默认值，或直接由 `2V(PCB)` 推出本机恰为两帧。

### 可借鉴的优化方向

优先级与最大往生早期问题不同：SDOJ 已修复跨轮发布／取用；虫姬二默认 1V 的配对测量表明主要时间位于帧尾等待。若继续降延迟，可评估在保持原出帧时刻的前提下，把采样与玩法更新安排得更靠近提交时刻，预留高分位工作时间和安全余量，而不是直接删除等待或提升游戏速度。本次分析不实现该时序改动。

独立项目 [futari-nx 的输入延迟研究](https://github.com/ChanseyIsTheBest/futari-nx/blob/main/docs/futari-notes.md#input-lag-2026-10-16-the-users-question-can-we-improve-input-lag-in-the-game-such-as-turning-off-vsync)报告其 PC 录像中首个手柄读取到 Present 约 16.7 ms，通过延后读取降到 5.6–8.2 ms，出帧率不变。这与上述方向相符，但其后端、补丁和测量起点不同，不是本合集的测试结果；其 Switch 显示时钟同步方案也不能直接移植成 Windows 修复。

本轮只交付 Ver1.5／Xbox360／1V 代表行。用户已取消其他 Frame Delay 档位及 Black Label 补测；上面的 Black Label 内容保留为既有静态证据，不扩写成其延迟实测。

最大往生的后续工作统一为 [Frame Delay 改进](SDOJ_LATENCY_PLAN.md)：3V 原路径、2V 稳定目标、1V 低延迟目标；借鉴虫姬二的完整结果交接，不照搬其地址、输入缓存或无限等待。具体的行为保持要求、配置设计和验收在方案中集中维护，本项不包含 0V，也不连带改动虫姬二。

以前的 Futari 音频 worker 等待修复不等于输入管线降延迟；当前约 17 ms 的结构也不是由那项音频修复创造的。

## G2 与虫姬二 Frame Delay 对照

G2 当前原生呈现策略最接近虫姬二的 **2V(PCB)**，不是虫姬二默认的 **1V(Fast)**。依据是实际提交函数及初始化开关的对应，而不是由 FPS 或手感换算帧数。Xbox360（dat12）和 Black Label（dat15）的普通玩法入口均已核对；其他模式共用主程序呈现端，但未逐一分析核心内部时序。

| 呈现环节 | 虫姬二 1V | 虫姬二 2V | G2 当前路径 |
| --- | --- | --- | --- |
| 帧尾入口 | 游戏自行等待 VBlank，然后 resolve／直接 swap | 标准 D3D Present | 标准 D3D Present，与虫姬二 2V 对应 |
| 立即交换开关 | 开启 | 关闭 | 关闭 |
| D3D 呈现间隔 | immediate，节拍由游戏等待负责 | 1 | default=0，在该 D3D 实现中按 1 处理 |
| 区分虫姬二 3V 的额外开关 | 关闭 | 关闭 | 关闭 |

两款游戏虽然共用 PC 输入与 D3D12 后端，进入后端前的原生提交策略仍然不同。G2 把同步安排在标准 D3D 命令流里，CPU 提前准备与 GPU 等待可以重叠；虫姬二 1V 则在游戏侧等待后直接交换。下面的 Xbox360 实测中，G2 两档的内部延迟差约 14～15 ms；2V 是呈现策略对应，不是物理按键到屏幕出光恰为 33.3 ms。

### 输入与绘图顺序

主循环 `820ED800` 先经 `820ECBC8 → 820FAB90` 更新输入，再调用 `82090FF0 → 82090940` 运行游戏。Xbox360 常态入口 `820CFD48` 先执行 `82091598 → 82094F38 → 820A7020` 转换按键，再进入 `820BB230` 的核心虚表 `+8`。核心读取的回调由主程序 `820B5478` 注册为 `82091690`，经 `82095190 → 820A6678` 返回映射状态。

dat12 的 `880202A8 → 88022C50` 在 `8814AC08` 取输入，然后运行 `88055FD0`；dat15 对应 `880202A8 → 88021CC0`、输入 `88158A80`、玩法 `8805F670`。这些入口同步返回到主程序，之后同一轮 `820912A8 → 8209A420` 处理绘图列表，`82092180 → 82095F48 → 820AD048` 调用呈现虚函数。没有在这条外层交接中发现 SDOJ 原先固定晚发布／晚取用的两轮滞后。原生 slowdown 会跳过部分玩法更新，不能算作固定输入排队。

### 呈现策略证据

- G2 渲染对象虚表起点是 `82012CA0`；`+8=820F4180` 处理命令，`+12=820F3E40` 调用 `82171340`。相邻的 `82012C30` 是其内部对象的另一张虚表，不能混用偏移。
- G2 `82171340` 与虫姬二 `820A5A68` 都是 63 条指令的标准 Present 包装；逐项核对后，11 处差异仅为调用目标及常量地址，两者 resolve 常量均为 1.0。G2 经 `821708B0` 安排同步，再经 `82170CE0` 调用 VdSwap；虫姬二对应 `820A4FD8`、`820A5408`。
- 虫姬二 `8216B148` 在模式 2／3 调用 `820A5A68`，模式 0／1 则绕过该包装直接 resolve／swap。模式 2 清除设备 `+24192` 的 bit 2 和 bit 0，呈现间隔设为 1；模式 3 的区别是打开 bit 0。模式 1 打开 bit 2，使用 immediate 间隔，并在 CPU 端等待 VBlank。
- G2 `820E7D00` 用行为标志 0 创建设备；`821703F8` 的缺省高位补充不改变上述两个低位。初始化参数的间隔字段为 0，复制到设备 `+13804` 后，在 `821708B0` 中与 1 一起映射为一次 VBlank。`82178988` 重设状态时保留这些值。其组合与虫姬二 2V 对应，不包含 3V 的额外开关。

本地复查入口 `.local/g2_latency_audit.py` 对原始区段执行 37 项指令／表项核对，并比对上述 63 条指令；结果在 `.local/analysis/g2-latency-r1/comparison.json`。default、dat12、dat15 原文件 SHA-256 与 `games/espgaluda2/inputs.json` 一致。只读分析不启动游戏、不改配置或时序。若继续量化差值，需匹配有效方向输入、对应绘图内容和最终 Present，不能把下一次出帧直接当成本次输入的画面。

## 狱门山的原生等待与输入顺序

对 XBLA 本体 0.0.0.4 做了只读复查，主程序 SHA-256 为
`b426e877eec7e34afe0c1314390a8f11c1728053668b6aea2efed2387d1bf401`。
工具 `.local/input-latency-v080-r1/audit_guwange_policy.py` 校验原文件、工具模式
区段收据及区段哈希，并核对 17 个生成函数的地址／标签、234 处分支目标和 17 组
有序指令；关键 load／store 另外核对原始编码。报告为同目录
`guwange-static-policy-r1.json`，不执行游戏。

- 主循环 `821E94C8` 先执行 `821EFEF8`；其中 `82217600 → 82253278` 调用
  `XamInputGetState`，再整理输入。主循环随后运行 `8219DFE0`，经虚函数提交工作，
  并等待原生 pending 完成。这里证明宿主输入刷新在本轮处理之前，尚未证明模块核心
  消费哪个输入样本，或哪个绘图批次首次响应。
- 渲染线程 `821F6AC8` 从原队列取工作，帧任务调用 `821F6EF8`。帧尾设置
  `82C0D578=1`，等它清零后才调用 swap 包装 `822653E8`。
- 初始化 `821EF010` 经 `82264FA8` 将 `821F6A18` 写入设备回调字段 `+16756`。
  `82269230` 的 source=0 分支进入 `82264C38`，后者递增 VBlank 计数并调用该回调；
  回调清零上述 flag。共享后端 `GraphicsSystem::MarkVblank` 确实以 source=0 派发。
  因此这不是任意线程完成通知，而是一次原生 VBlank 门控。
- swap 包装还有受设备标志及间隔 `+13808` 控制的命令同步；渲染循环会动态设置该
  间隔。同步命令的位置和它约束的下一轮工作需要区分，不能看到两处等待就相加为
  固定 2V，也不能只凭创建设备的 bit 0 就叫作虫姬二 3V。

当前可下的结论：移植版仍保留这次交换前的 VBlank 条件；polling 改通知降低的是
CPU 成本，没有据此缩短一个游戏周期。原作代码在 Xenia 中有同样的等待结构。
两边是否得到相同的输入到首响应总周期，仍取决于核心消费、队列年龄和运行中的
呈现间隔；本次不把这些静态位置换成未经测量的毫秒数。

Xenia的第一轮控制流定位还确认：主循环`821E9664`的虚调用实际落在
`821EBA10`，只返回1，并非核心更新。后续两个提交调用落在`821F7620`／
`821F7720`，对应原生队列的type0／type1条目；绘图列表绑定调用落在
`821F6628`。因此不能沿“刷新输入→这个虚调用→下一次Present”直接算玩法延迟。
记录为`guwange-control-targets-r1.json`，217,144条完整事件、零溢出，
4次测试输入均由原API读到；场景尚未进入玩家关卡。

同EXE、同配置关闭客体指令观测的控制轮取得69,318条完整事件，3次输入均到达

### 狱门山：输入端口与首响应画面的两轮差别

代表场景为 **XBLA 0.0.0.4／Arcade／Shishin／Stage 1**，两边只发送相同的左右方向

与独立发布的输入逐次核对；不是把导出描述符或模拟 CPU 寄存器误当作按键。

### 用现有数据先做理论判断

用户允许先依据源码和已有采集完成理论分析，不等待新一轮显示采集。旧记录可以
使用：其来源、场景和呈现路径已知，仍能支持对应测试条件下的事实及量级判断。
当前实测、历史实测和条件推导分开标注，不把“旧”直接等同于“无效”。

进一步核对版本：v0.7.5、当前 v0.8.0 冻结源码 `c427257` 和工作树的
`d3d12_presenter.cpp` Git blob 均为 `2822c244255d26fa1e542cb0742e32151f813d53`；
旧／当前 `presenter.cpp` 均为 `da3e39d16c8c664e9d3d349ed9a3222fb08f0fe1`。
因此交换链呈现策略和 ready 输出交接没有版本变化。GPU 命令、resolve 和等待实现
有过优化，Windows 的实际合成／翻转路径也由运行现场决定；这支持复用旧呈现数据
建立条件模型，但不支持宣称旧毫秒数就是当前每次运行的显示延迟。

现有证据已支持两个结论：

1. 虫姬二默认 1V 的玩法读取到对应 Present，在两边都约 17 ms。没有证据表明
   Xenia 在这一段必然比移植版多一整帧。
2. 旧的同机呈现记录中，移植版独立翻转的 Present 后段均值为 0.919 ms；Xenia
   桌面合成为 11.178 ms。两种现场输出路径的后段确实相差约 10 ms 量级。不是
   对所有环境固定成立的差值，也不是保持全部条件相同后孤立测得的 DWM 成本。

可以据此给一个明确标注假设的预算模型。起点为**输入状态已经到达、可被游戏读取**，
终点为系统显示事件。假设游戏正常 60 Hz、输入到达相位均匀、没有额外丢帧，且
各自仍采用旧记录中的呈现路径和相近后段开销：

`模型均值 ≈ 等待游戏读取（16.67 / 2）+ 当前核心到 Present 样本均值 + 历史 Present 后段均值`

| 条件模型，非端到端实测 | 移植版，独立翻转 | Xenia，桌面合成 |
| --- | ---: | ---: |
| 等待游戏读取，均匀相位假设 | 8.33 ms | 8.33 ms |
| 当前核心读取 → Present，60 次样本均值 | 17.046 ms | 16.834 ms |
| 历史 Present → 系统显示，样本均值 | 0.919 ms | 11.178 ms |
| 模型的平均时间量级 | **约 26 ms** | **约 36 ms** |

这里计算的是条件模型的平均预算，没有相加独立中位数，也不给模型编造实测 P95。
USB／设备、Windows／SDL 尚未使状态可读之前的时间，以及指定扫描位置和面板响应
另计。它说明可能的差距来自哪里，不能用作当前版本已经实测快 10 ms 的宣传结论。

1V 标签只描述游戏侧时序；Present 的 immediate 也不表示屏幕瞬间显示。保持原始
游戏时序的 CPU／GPU 效率优化，首先减少执行成本，并不自动消除约一帧的帧尾等待。
后续真正缩短输入响应，应分别评估更晚取输入、游戏／输出交接和实际呈现路径。
[DXGI Present 的同步与队列语义](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgiswapchain-present)。

| 状态发布 → 对应帧 Present 开始 | 24.906／32.587 ms | 24.596／31.897 ms |

总计按每次输入的起止时刻直接计算，没有将分段中位数相加。当前证据说明双方都约
一帧内部延迟；不足以将约 0.16 ms 的差值解释成两套运行方式的固定性能差距。
读取输入之前还存在相位等待：60 Hz 玩法更新中，新状态可能刚好赶上本轮，也可能
等接近一个 16.67 ms 周期。因此，1V 内部管线通常对应约 1～2 个周期的软件总计，
而非从任意按下时刻开始恒定 16.67 ms。

原生运行时沿输入写入地址、完成事件对象、绘图列表地址／字数／所有者／锁、
guest swap 包、ready mailbox 和 paint 身份关联。Xenia 使用相同的原指令位置和
交接校验，固定源码 `291f0c9be398a3e0a0e29f378cbd564fa28c55a9`。

### 约 17 ms 花在哪里

以下为带连续图像的原生 R6，60 次输入的分段中位数。每一行是墙钟区间，
并非全部都是 CPU 在执行计算。

| 区间 | 中位数 | 含义 |
| --- | ---: | --- |
| 玩法取输入 → 玩法更新返回 | 0.115 ms | 本轮逻辑更新 |
| 更新返回 → 绘图列表发布 | 0.052 ms | 整理本轮绘图数据 |
| 列表发布 → 主线程消费 | 0.023 ms | 玩法／渲染线程交接 |
| 消费列表 → FrameDelay 分支 | 0.432 ms | 处理绘图指令、进入帧尾 |
| FrameDelay 分支 → VdSwap 调用位置 | 15.981 ms | 主要是 1V 等待；也包含 resolve／swap 准备 |
| VdSwap 观测 → 对应 Present 开始 | 0.457 ms | 输出线程交接和提交，不能当作纯 GPU 执行时间 |
| 玩法取输入 → 对应 Present 开始，逐次总计 | 16.955 ms | 本轮软件管线 |

帧尾入口 `8216B148` 在 1V 分支等待原生 VBlank 计数变化，然后 resolve／swap。
当前通知等待在 `8216B244` 保留原谓词，只将等待期间的空转改为休眠及通知唤醒。
15.981 ms 这个区间不能叫作“绘图计算用了 16 ms”。

`1909642d6035ba13bb48fcaad9adc045315c6a7c0ef1a3484675cd245113668b`，

合集手柄使用 SDL 3：事件进入 pending 队列，`GetState` 先处理已到达事件，并向
UI 线程异步请求 `SDL_PumpEvents`；该调用不等待一次新的硬件采样。Xenia 此固定版本

SDL 路径同样将 pump 排到 UI 线程。因此不能给“Windows＋SDL”填一个普遍固定的
毫秒数，设备报告周期、驱动和事件调度都会影响状态何时进入游戏可读的位置。
[SDL 的线程要求与事件更新说明](https://wiki.libsdl.org/SDL3/SDL_PumpEvents)。

### Immediate 之后与可优化方向

当前 D3D12 使用 flip-discard、`Present(0, RESTART | 可用时的 ALLOW_TEARING)`，
ready mailbox 取最新可用输出。交换链有多张资源不表示固定额外排队同样多帧。
这里的 immediate 允许尽快提交、替换旧输出；随后仍经过 GPU 完成、Windows 的
呈现／合成路径和显示器扫描。CPU 的 Present 返回时间无法代表某个屏幕位置已发光。
[Microsoft Present 说明](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgiswapchain-present)、
[flip model 与 DWM 的关系](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/dxgi-flip-model)。

本机这些运行的 DXGI 显示统计没有提供可用的图像显示时间。实体开关／USB 到窗口
处理器之前、SDL 设备实际报告时刻，以及扫描／面板出光仍没有数值；本节已量出的
完整软件端点是“窗口键处理器 → 首次响应图像对应的 Present”。

RTX 4080 的设备扩展列表包含 `VK_EXT_present_timing` revision 3。进一步在实际 Win32 窗口表面查询，返回 `presentStageQueries=0x5`：支持队列操作完成及图像首个像素输出，不支持首个像素可见；绝对时间调度为不支持，相对时间为支持。这只是可查询能力，尚未取得逐帧反馈。探针不请求定时调度，后续以原有呈现方式采样。[阶段及能力定义](https://docs.vulkan.org/refpages/latest/refpages/source/VkPresentTimingSurfaceCapabilitiesEXT.html)。

### 显示器后段的理论预算

刷新率给出显示周期 `R = 1000 / Hz`，不直接给出 Present 到指定像素发光的总时间。
从 Present 开始的链路还包含尚未完成的 GPU 工作、驱动／合成／呈现排队、等待
允许更新的时刻、扫描到观测位置、显示器处理及像素响应。阶段可能重叠，实测总计
仍应使用同一画面的起止时刻。

| 固定刷新率 | 显示周期 R | 空队列、图像已 ready、均匀到达相位时，等下次刷新均值 |
| --- | ---: | ---: |
| 60 Hz | 16.67 ms | 8.33 ms |
| 120 Hz | 8.33 ms | 4.17 ms |
| 144 Hz | 6.94 ms | 3.47 ms |
| 240 Hz | 4.17 ms | 2.08 ms |

这是固定刷新、同步翻转的理想模型：等待约在 0～R 之间；每个已经排在前面的
FIFO 请求还可能增加一个刷新周期。不是所有 Present 都固定等半帧。
[Vulkan FIFO 的队列与刷新规则](https://docs.vulkan.org/refpages/latest/refpages/source/VkPresentModeKHR.html)。

常见逐行扫描模式中，从一轮扫描开始到屏幕中心约为半个扫描周期，到底部接近
一个；精确值由有效扫描时序、面板方向及观测坐标决定。以 144 Hz、有效扫描约等于
6.94 ms 的理想情况为例，图像 ready 后等刷新平均 3.47 ms，再扫到中心约
3.47 ms，即约 6.94 ms，另加显示器处理和像素响应。GPU ready 前的时间另计。
这不是当前显示器实测，也不假定画面顶部和底部同时改变。
[显示延迟的三个组成部分](https://www.nvidia.com/en-us/geforce/guides/gfecnt/202010/system-latency-optimization-guide/)。

允许撕裂的 immediate 路径可在正在扫描的一轮中途换图，不必先等下个 VBlank；
但已经扫过的位置仍要等下一次经过，整幅新图也不会同时出现。因此历史 0.378 ms
的 Present→系统显示事件不意味着整屏已在 0.378 ms 内发光。
[DXGI 呈现路径](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/dxgi-flip-model)。

VRR 会改变等待下一轮开始的规律，不能继续机械套固定刷新均匀相位表；实际扫描
速度也不必等于当前游戏 FPS。虫姬二的 60 Hz 游戏更新周期约 16.67 ms，当前
144 Hz 桌面显示周期约 6.94 ms，两种“帧”必须分开记录。面板宣传的 1 ms 响应
也不是 Present 到显示的总延迟。

最终延迟表还须包含发光端，统一注明 **144 Hz／屏幕中心／理论预算**，与实测列
分开。用 `D` 表示尚未测得的显示器内部处理及像素响应。以下起点是图像已经 ready、
呈现引擎已可采用它，而不是 CPU 的 Present 调用开始；假设没有 GPU／DWM／WSI
积压、固定逐行扫描、扫描时间近似 6.94 ms，且到达相位均匀：

| 144 Hz 屏幕中心的理想发光预算 | 图像 ready → 中心像素响应 |
| --- | ---: |
| immediate／允许中途换图 | 平均约 **3.47 ms + D**；等待扫描经过该位置约 0～6.94 ms |
| 同步翻转／空 FIFO | 平均约 **6.94 ms + D**；等刷新平均 3.47 ms，再扫到中心约 3.47 ms |

immediate 的 3.47 ms 已是等待扫描经过指定位置的预算，不能再加一次“中心半帧”。
若采用历史 Present→系统显示事件数据，其中已经计入的 GPU／刷新／合成等待也
不得重新加一遍；该事件相对于扫描起点的相位没有标定，不能直接再加 3.47 ms 就
当作当前发光总计。`D` 未知，不填零；后续结果须保留发光端列及其理论／实测标签。

#### 四作原始程序的输入缓存边界

已独立读取四份原始 eboot 的 ELF 导入／重定位，定位 `scePadRead` 的 PLT 跳板，
再用 LLVM 解码确认调用位置；不是在文件中搜索某个像 E8 的字节就认定调用。
原始 signed displacement 与下表调用目标一致。四作都在同一查询封装内请求最多
63 份报告，并以对象 `+0x1d` 缓存有效位避免重复查询：

| 数据版本／原程序 | 输入查询封装 | scePadRead 调用 | 缓存命中直接跳到返回路径 |
| --- | --- | --- | --- |
| 绊地狱 01.02 | `1ea660` | `1ea6d1` | `1ea78e` |
| 大往生 01.04 | `1dc0c0` | `1dc105` | `1dc1ae` |
| ESP Ra.De. 01.04 | `216dc0` | `216e31` | `216ede` |
| 弹铳美版 01.00 | `1dc5a0` | `1dc611` | `1dc6ce` |

缓存未命中才刷新 API，成功路径保存返回数量并置有效位。命中后会绕开
`scePadRead`，返回已有结果。因此玩法的某个按钮 getter 不等于一次新硬件采样；
必须继续追踪哪份报告真正被核心使用。63 是一次请求容量，不是 63 帧延迟，
也不证明游戏总在消费最旧一份报告。

本地复查入口为 `.local/input-latency-v080-r1/audit_ps4_pad.py` 和
`check_ps4_pad_cache.py`；报告 `ps4-static-pad-r1/report.json`、`cache-check.json`
绑定原文件／解码 ELF／LLVM 身份。后者另外检查四作共 16 处原始 guard、请求容量、
有效位写入及条件分支编码。ESPRaDe／弹铳的明文 SELF 仅在私有分析目录重建
ELF 视图，原文件没有改动。这里确定的是输入查询边界，不是核心消费或出光实测。

进一步将缓存重置连接到了四作自己的引擎调度。控制器对象通过基类注册到
manager `+0x80` 阶段；节点适配器调用控制器虚表 `+0x10`，其实际方法清除
`+0x1d/+0x1e`。引擎循环先处理这组节点，并在本轮状态虚表 `+0x28` 更新前
执行批处理收尾。收尾既会调用保留的工作函数，也会通过原始 Signal／Wait
Semaphore 导入完成并行任务；不是仅把任务发布出去就继续运行核心。

| 原程序 | 缓存重置方法 | 引擎循环 | 批处理收尾调用 → 本轮状态更新调用 |
| --- | --- | --- | --- |
| 绊地狱 01.02 | `1ea7d0` | `19bc20` | `19bd08` → `19bd30` |
| 大往生 01.04 | `1dc1f0` | `192b30` | `192c08` → `192c42` |
| ESP Ra.De. 01.04 | `216f20` | `1caae0` | `1cabc8` → `1cabf0` |
| 弹铳美版 01.00 | `1dc710` | `192c40` | `192d28` → `192d79` |

因此，这层缓存没有“本轮先用旧输入、更新之后才使新采样可用”的固定一轮交接。
它在本轮更新之前失效，之后的首次查询可取得新报告，同一轮的后续查询则复用。
这不是证明四作总共只有 1V：状态更新内部的模块回调、报告取用顺序、街机核心
本身的响应以及绘图结果年龄仍须区分。慢帧或降低核心更新频率时，也不能仅从
这个外层循环推导固定毫秒数。

复查工具 `audit_ps4_reset_phase.py` 和结果 `ps4-static-pad-r1/reset-phase-r2.json`
分别绑定四作原文件，核对重置方法字节、虚表重定位、构造注册、节点适配器、
同步／批处理分支和更新调用位置。并行收尾中的 semaphore NID 由每份原 ELF
的 PLT／GOT 关联确认，运行时 `native_semaphore.cpp` 对应真实的 Signal／Wait。
这推进了游戏原程序的时序分析，没有改变输入实现或重新运行游戏。

输入端 `native_pad.cpp` 的 sampler 间隔为 16,666,667 ns，但 `ReadReports` 在
键盘／SDL 按下 latch 存在时会立即 `Sample()`；`sdl_gamepad.cpp::Poll` 会调用
`SDL_UpdateGamepads()` 并读取最新状态。因此数字按钮／十字键的按下不是固定先
等 sampler 再等游戏、无条件增加两次半帧。松开和普通摇杆轴变化不走同样的按下
latch；没有其他触发时可能先等 sampler，随后再等游戏读取。两种输入必须分列。

固定 shadPS4 的 4 ms 定时器执行 `PollState()`，按钮和轴事件另直接更新状态并
发布历史；这个定时器既不是所有按钮必须经过的额外 4 ms，也不是整个设备前段
只有 4 ms 的保证。双方都存在事件分发、线程调度和游戏取样相位，不能由
“16.67 ms vs 4 ms”直接算出移植版落后 12.67 ms。

输出端的生产路径不是同步上传 fallback。`native_video.cpp` 先预留原生软件时钟的
下一出帧机会，`NativeResidentGpu::Present` 先准备 GPU 快照，再等这次已预留机会，
然后 `host/presenter.cpp::Complete` 确认快照复制完成、发布 ready 身份。准备跨过
目标时不再重新预约下一整帧。输出线程只保留一个待取 ready，较新的会替换尚未
取走的旧 ready；已经取走的快照及 WSI 呈现资源另有各自 fence 生命周期。

这能排除“ready 队列无限积压”，不能排除输出线程已有的在途工作、WSI FIFO、
Windows 合成及显示扫描。默认 FIFO 仍可能等桌面刷新；快照替换也意味着某次
输入的第一幅响应可能没有显示，测量必须统计被替换，而非只挑后面的成功帧。

尤其要区分 `Complete` 返回／原生 flip 通知、`vkQueuePresentKHR`、呈现资源 fence
和显示时刻：前者在 ready 发布后就可完成，输出线程的 Present 还在后面。
maintenance1 fence 也只保证规定的队列／资源生命周期条件，不保证整个画面已经
显示。不能拿它冒充屏幕时间。
[Vulkan 呈现 fence 的定义](https://docs.vulkan.org/refpages/latest/refpages/source/VkSwapchainPresentFenceInfoKHR.html)。

因此四款 PS4 目前不能仅因共用后端就填相同几 V，也不能借用虫姬二 D3D12 的
0.378 ms 历史后段。后续理论分解的逐作重点是核心输入样本及响应批次年龄；公共
前段、ready 交接和 FIFO 模型不必各开一轮游戏重复证明。

### 虫姬二：immediate 后仍有显示等待

原作 1V 的 immediate 与 Windows 的 `Present(0, ...)` 是不同层的开关。当前合集和基线 Xenia 的 D3D12 都以 interval 0、RESTART 及条件式 ALLOW_TEARING 提交，Windows 实际显示路径仍可能不同。[Present 定义](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgiswapchain-present)不保证调用返回时像素已经出光。

### 地址等待与通知后的长尾

成功等待的恢复路径改为独立 waiter 的原子结果与 Windows `WaitOnAddress`／`WakeByAddressSingle`，不再重新争用共享 semaphore gate。队列次序、完整 credit 预留仍在原 gate 内完成；先建立通知对象的拥有链，再 release 发布结果。等待以 acquire 读取结果，早于停车的通知不会丢失，虚假唤醒继续检查原截止时间。只有超时退休才重新取得 gate，并再次检查是否已获授予；已预留的成功不会被超时覆盖。取消、删除及通知对象生命周期沿用原语义，复用仍有独占所有权和显式发布屏障。依据为 [Microsoft WaitOnAddress 合同](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitonaddress)；不依赖其唤醒顺序实现 guest FIFO。原 CV 路径保留作诊断对照，不改 CPU 映射、电源或优先级。

日志的 `native_semaphore_wait_timing` 现在包含 `wake_began_clock_us`、`wake_finished_clock_us` 和 `address_wait`，可区分发通知之前与之后的延迟。成功可能早于通知调用／结束被观察到，此时相应字段为 0 或通知结束晚于恢复，不作负耗时相加。CV 恢复仍包含重新取 gate；address 的成功路径不包含此步骤。WPR 的 CPU 调度采集因当前非管理员权限未能启动，已核对未在 recording，故没有用内核调度 trace 证明剩余时间全属 Ready 排队。

两种传输各完整执行 26 个 semaphore 子例，共 52 项；包含成功是否需要重取仍被夹持的 gate、不得在首个 semaphore 发布后切换传输，以及全部原 FIFO／优先级、credit、超时、取消／删除和生命周期场景。完整 73 项原生和 373 项源码（含 13 项 bench 协议）通过，日志 `.local/v03-address-wait-r2-{build,source,native}.log`。GPU DLL 未改，原 API7 配对及既有图形机制证据沿用，不写成新测。

### 信号量交接的软件批次

信号量热路径现在使用每线程两个弱引用句柄缓存，减少 work/done 交替操作的全局表锁；删除仍在状态锁内判定，句柄不复用，缓存不延长已删除对象的生命周期。客体线程优先级由创建时不可变的快照直接保存在 TLS，不再每次等待都锁线程注册表；以后实现运行中修改优先级时须同步修改此合同。FIFO／优先级顺序、完整批量 credit 预留、超时、取消及删除返回值均不改变。

唤醒通知移到释放 semaphore gate 之后。队列及无分配的通知链共同持有 waiter，确保等待线程提前返回甚至退出后，notifier 使用的 condition_variable 仍然有效。每线程只在唯一持有 waiter 时复用它；旧 notifier 尚未释放时重新分配，不能覆写仍被通知的 CV。原生检查包含等待线程先退出、带旧通知开始第二次等待、跨线程删除缓存句柄、优先级继承和未托管线程默认优先级；24 个 semaphore 子例、18 个 thread 子例及完整 73 项原生入口均通过。源码 372 项通过。没有修改 CPU 映射、系统电源、进程优先级或游戏任务数。

### 实际处理开销与离线重放的区别

开发构建可用 `--d3d12_profile_cpu_work=true` 按绘图阶段累计线程 cycles 和墙钟时间，默认每 60 次交换输出一组 `CPU_WORK`；`frames` 给出累计帧数。`subset_*` 是嵌套子集，不能再次加到总和；`CPU_UPLOAD` 记录实际上传字节。普通玩家构建不编译这部分采样。采样调用自身有成本，因此它用于定位阶段，最终进程 CPU 对照须关闭采样。

离线基准的 `--bench_alternate_overwrite=true` 可比较跳过整页覆盖前旧内容上传的候选，不能同时交错另一项优化。此路径有约 22% 的离线命令处理墙钟收益，但真实同录像的四次开关对照没有确认收益，默认不启用。快照重放会制造重新上传，需以实际 `CPU_UPLOAD` 核对是否属于真实热点。相同着色器常量去重也因未测得收益而移除。

服务只监听 127.0.0.1 的随机端口，使用原虫姬二协议和全新 SQLite。终端与现场目录的 `service.json` 给出临时 API 根地址；将它临时填入唯一根 INI 的 `[game.futari.community]` 中的 `endpoint`，并显式设置 `enabled = true` 和测试昵称，即可从游戏原生流程验证榜单、成绩及录像。客户端自行追加 `/games/futari`，不把完整游戏路径再填进 endpoint。服务默认 30 分钟后停止，Ctrl+C 可提前结束。

输出必须是合集 `.local` 内不存在的新目录，不复用数据库、不连接正式服务，也不更改服务端默认路由。验证结束后关闭游戏并恢复 INI；保留现场可供只读分析。未完成的待传记录仍属于原服务地址，不能改填正式地址以补传本机测试成绩。
