# 最大往生 Frame Delay 改进方案

本项统一称为 **最大往生 Frame Delay 改进**：在原有约 **3V** 的软件管线之外，提供 **2V**（`balanced`）和 **1V**（`low`）两条改进路径。1V 参考虫姬二“本轮完成、本轮取用”的线程交接方式。减速统计与训练重入崩溃已在 v0.4 修复；结合后续持续输入检查和玩家最新实战反馈，**v0.6 默认采用 1V**，保留 2V 平衡档和 3V 原始路径。**本次不提供 0V。**

体验目标是响应更快，同时保持玩法、原作减速、录像兼容、画面完整和出帧节奏。1V 的改动范围比 2V 大，但两档采用相同的正确性标准，不以降低兼容性或增加卡顿作为代价。

当前正在实现与验证。适用对象是合集已经支持的光盘本体 default、CA022100、CA022110；不要求安装 TU 或音乐补丁。v0.4 的界面需求另在[实施计划](IMPLEMENTATION_PLAN.md#v04-已登记需求)中维护。

### 当前实现状态

`games/sdoj/latency/` 已接入两模块的真正完成确认、完整原生交换、后段去重和模块生命周期。宿主接受 3／2／1，v0.6 缺省为 1，已有显式档位保留。两模块进关、暂停返回、录像对照及后续减速统计修复的回归范围见 [TEST_MATRIX](TEST_MATRIX.md)；默认值调整不改变现有交接、超时回退和原作减速逻辑。

新 Arcade HD 录像已完成保存后的冷启动回放。减速计算现在保留原绘图管线的统计所属帧，不改原生公式；修正后的同构建 2V／1V 对照，在原生结束请求前的 5504 次更新中，画面命令、状态、减速操作数和等待深度全部一致，均有 131 次 depth=2。两份录像已有的原生声音请求及分发顺序对照一致。

原版 3V 的 A/A 对照另发现未初始化的背景地图边缘：相同程序和存档可分别出现 131／212 次 depth=2，第 2845 次更新多出 36 块背景命令。反推边缘单元可以精确重建全部多余命令；现已在新分配地图返回后清零完整分配，三档共用，不过滤绘图命令。它与提前绘图改变统计年龄的问题分别处理。

修正后的同构建 Arcade HD 完整回放已补齐模块 1 的输出链。第一关正常速度的 2125 次更新全部关联到首次 Present：3V／2V／1V 中位为 49.957／33.266／16.847 ms，最大为 51.585／34.002／17.690 ms；分别跨 3／2／1 个输出周期。1V 与 3V 在原生结束请求前的 5505 次更新中，命令、状态和等待深度逐项相同，均有 131 次 depth=2；四次减速操作数差异对应原版读取相邻绘图统计的时序差，未改变 depth。2V 的这轮初始化少一次就绪轮询，不能把整段编号直接相等作为已通过；原记录和失败比较保留，具体边界见 TEST_MATRIX。

关闭细粒度 latency／output／audio trace 后的 2V／1V 常态检查已完成：第一关内分别统计 2290／2170 个呈现间隔，平均均约 16.667 ms，最大 17.430／17.530 ms，无超过 20 ms 的间隔；三路音频均无补静音，队列峰值相同。两轮保留 `sdoj_logic_trace`，用来界定原生第一关和结束状态，不称关闭全部观察器。初始化有两种就绪轮询长度，2V 和 1V 均出现过；相同初始化类别的两组完整 2V／1V 回放，分别在 5504／5505 次更新中连同减速操作数逐项一致。

普通短按和切出／切回、持续输入与松键的已完成范围见 [v0.4 专项](IMPLEMENTATION_PLAN.md#默认-3v-发行与-1v-后续专项)；测试 pad 的持续输入结果属于游戏逻辑路径，不代替实体设备测量。玩家随后实际对比 1V／3V，并确认 v0.6 默认使用 1V。已有显式档位不覆盖，已发布包不回改；不为默认值调整重放全套录像。

1V 的 r4 日志前段有 5526 份可关联的首次结果，输入消费至对应 Present CPU 返回中位 16.845 ms、p95 17.302 ms、最大 18.249 ms，另有 1089 次旧结果重复呈现。该结果来自模块 2；细粒度 trace 达到上限后的部分不纳入完整输出链结论。它说明当前路径已取得约一帧的软件管线结果，不代替实体按键到屏幕测量。日志及修复前后对照见 TEST_MATRIX。

输入前段直接复用原生 `88044960`，在 `880451D4` 解析命令前结束，晚段仅跳过已执行的输入部分。`scripts/Test-SdojPrefix.ps1` 从本地生成物准备不含玩法循环的隔离 fixture，两模块各 1292 组输入通过独立端口 oracle：包含 action 0–63、双玩家、映射组合、±9000 阈值和加入控制器副作用；另核对原生栈／LR／非易失寄存器、解析入口五个 live-through 值及晚段不再次查询输入。fixture 的生成正文只留在 `.local`，不纳入 Git。这不替代实际短按／失焦、录像输入来源和输入到画面延迟检查。

隔离 fixture 现直接复用生产 `GuestCall`，额外验证完整 PPC 上下文和宿主浮点控制状态，包括本机 FTZ 改动及 C++ 异常退出后的恢复。固定录像对照的 `sdoj_logic_trace` 默认关闭，记录完成命令 SHA-256、等待深度、原生状态及结束请求。输入字段是复制前的 live 端口，录像解码发生在其后，不能把这些字段当成已解码的录像输入。对比工具要求明确连续窗口，不重新对齐或忽略差异；结束窗口由原生退出状态界定，不以删除失败尾帧取得通过。

首轮实际 Xbox360／SHOT 训练证实了提前交换的工作路径，也发现暂停后恢复的一次性记录不能以宿主帧号匹配：暂停期间原生回调及唤醒计数可以不前进，主循环仍会前进。记录现以模块代、原生唤醒计数、交换序号与缓冲匹配，暂停后的对应调用仍须结清。r2 实际旧录像的暂停／恢复、自然返回及两模块切换通过；首轮异常记录仍保留。r2 首次结果输出中位约 33.134 ms，其进入／结束及调度停顿样本留在历史记录；当前第一关同构建三档对照和常态节奏以上面的修正版结果为准。具体证据及剩余范围见 TEST_MATRIX。

来源分析保留每次真实取用与输出，另列 `first_result_*`，把同一结果在暂停／减速期间的重复呈现与第一次呈现分开；不把长时间停留画面的年龄当成新输入结果的延迟。原始等待及输出关联要求不放宽。

## 目标与计时口径

这里的 3V／2V／1V 表示 **正常速度游玩时，游戏消费本轮输入至对应画面 Present 返回的软件管线帧数**，以当前约 60 Hz 的客体帧周期计。外部按键等待下一次采样、设备传输、GPU 完成和屏幕扫描另计。原作减速所需的额外游戏等待继续保留。Frame Delay 是本次 PC 改进的功能名称与档位表达，不要求最大往生原生菜单已经存在同名选项。

| 档位／内部策略 | 命令完成后等待发布 | 发布后等待下一轮取用 | 最终原生帧等待 | 正常速度结果／目标 |
| --- | --- | --- | --- | --- |
| 3V／`original` | 约一帧 | 约一帧 | 保留约一帧 | 原路径已测约 50 ms |
| 2V／`balanced` | 保留原来约一帧 | 消除 | 保留 | 目标约 33 ms，两帧 |
| 1V／`low` | 本轮完成后即发布 | 本轮取用 | 保留 | 目标约 17 ms，一帧 |

目标是减少画面的排队年龄，游戏仍按原作速度推进。正常帧必须稳定满足目标；安全回退和原作减速分别统计，不能把只偶尔命中的一帧结果当作完成。

这三档选择的是完整的输入／计算／发布策略，不是在 Present 上设置同步间隔，也不是机械增删固定毫秒数的 Sleep。两条改进路径均保留最后的原生出帧节拍；不在本项中取消同步、改为 0V 或引入预测／回滚来争取更低数字。

对于同一份由输入 I 生成的画面，正常速度下的计划顺序如下：

| 主循环时刻 | original | balanced | low |
| --- | --- | --- | --- |
| 第 N 轮 | 后段消费 I，完成命令 | 同 original | 前段准备本轮输入，消费 I，完成、发布并绘制 |
| 第 N+1 轮 | 先绘制旧画面，后发布 I 对应命令 | 先发布 I 对应命令，本轮绘制 | I 对应输出通过保留的原生节拍点 |
| 第 N+2 轮 | 才绘制 I 对应命令 | I 对应输出通过原生节拍点 | 后续帧正常推进 |
| 第 N+3 轮 | I 对应输出通过原生节拍点 | 后续帧正常推进 | 后续帧正常推进 |

验收还必须从宿主输入事件／输入快照身份追到同一输出图像，避免通过更晚才标记“消费输入”，或消费旧输入，得到虚假的短延迟。

## 作为设计依据的已确认事实

[完整分析](ANALYSIS.md#原生渲染队列与最终输出软件链路结论)的 2,216 条链均经过真实命令缓冲、原生绘图队列、帧结束消息、同一个 XE_SWAP 和输出图像：

- 输入消费到 renderer 取用中位 32.982 ms，源头正是晚发布、晚取用。
- 原生帧结束回调等待中位 15.618 ms；VdSwap 到 Present CPU 返回中位 0.325 ms。
- 两次存活自机方向输入已经改变第一份消费该输入的命令，未发现还需等待下一次玩法更新才能响应。

本次设计进一步检查了已接受的相同日志和两套模块代码：

| 检查 | 结果及设计意义 |
| --- | --- |
| balanced 提前发布的可观测前提 | 2,216 条链均有已完成命令、等待中的生产线程、countdown=1、尚未发布的对应缓冲和匹配交换序号 |
| 命令完成至下一轮原有取源点的余量 | 最少 13.524 ms，中位 16.169 ms；balanced 在这些样本中无需等新计算 |
| 读取输入至命令完成 | 中位 0.123 ms，p95 0.330 ms，最大 0.595 ms |
| 读取输入至进入游戏等待函数 | 中位 0.131 ms，p95 0.341 ms，最大 0.717 ms；未来提前唤醒产生的调度等待不包含在这里 |
| `active_writer == 0xFFFFFFFF` | 写入开始时已经设置，写完以后仍保持；它不是完成信号，必须新增明确的完成交接 |
| 发布动作 | 同时切换写入区、绘图区及相关渲染元数据；不能只修改一个 published 指针 |
| 输入转换 | renderer 的 `88044960` 先更新缓存输入端口，再调用命令解析；`880342D8` 从这些端口构建玩法掩码 |

最后一项决定了 low 必须包含输入适配：把原来的掩码构建函数直接前移，会读到尚未更新的端口。两套模块的虚表均已核对，相关取值方法读取 renderer 对象 +68、+70、+71；方法地址各不相同，不能套一个固定偏移。

上述 2,216 条样本均为等待深度 1，来自同一次 Xbox360／Shot 训练现场。它们支持正常速度方案的机会和预算判断；深度变化、录像及另一模块仍需在实现后做针对性验收。本次只做离线复查，没有重新启动游戏。

## 参考虫姬二的交接逻辑

[虫姬二的本地代码分析](ANALYSIS.md#虫姬二与最大往生的输入到输出延迟)已核对 Ver1.5／Xbox360 和 Black Label／Xbox360 两模块。在普通 depth=1 路径中，主线程清除旧完成事件、唤醒玩法线程、等待本次完成，再调用绘制；玩法线程恢复后取得输入、更新逻辑、生成并整理绘图数据，之后才发送完成通知。这是 1V 方案的结构参考。

虫姬二原生 FrameDelay 的新建配置和恢复默认值为 `1V(Fast)`，相应主程序路径在提交前等待出帧节拍。原生默认值与线程顺序已经静态核对；合集虫姬二同口径的输入到 Present 数值尚待量化。最大往生的 1V 目标仍由自身来源链验收，不借用另一游戏的档位名称或数字作为通过依据。

| 借鉴点 | 最大往生中的具体落实 |
| --- | --- |
| 玩法开始前准备有效输入 | 在原生 action 状态更新后建立本轮快照，完成最大往生专属端口／掩码转换；录像继续使用其逻辑帧输入 |
| 完整结果才通知消费者 | 命令、元数据、等待深度和下一等待基线全部就绪后，发布有请求身份的完成记录 |
| 本次完成后才开始取绘图数据 | 在进入绘图资源／队列锁之前完成交接，再调用原生完整交换，让 renderer 从头读取同一批数据 |
| 原有玩法线程继续工作 | 调整请求与交接位置，不把玩法搬进主线程，不新增第二套玩法循环或设备轮询线程 |
| 保留原作节奏 | 维持原有逻辑更新次数、减速计数和最终 VBlank 等待，只减少结果的排队年龄 |

1V 的目标顺序为：

`本轮输入就绪 → 唤醒原玩法线程 → 本轮命令完整 → 完成确认与原生交换 → 本轮绘制 → 原生节拍出帧`

两款游戏的输入缓存、缓冲布局和资源保护不同，复用的是交接原则，不是函数地址或同步对象。虫姬二原生握手中的无限等待不直接移入最大往生；这里使用带截止时间的等待与迟到请求排空，避免工作线程唤醒变慢时把主线程无限卡住。单纯再读一次 XInput，也不能替代后续完整交接。

## 行为保持与验收要求

“除了响应更快，其他游玩行为不变”是设计目标和验收条件。画质、减速与录像兼容均保持原有要求，按下列条件做同构建对照，确认收益和行为一致性。

| 项目 | 必须保持的行为 | 验证与风险控制 |
| --- | --- | --- |
| 玩法与输入 | 每个逻辑帧恰好更新一次；按键映射、边沿和连发规则不变 | 对同一逻辑帧输入比较转换结果、更新次数和关键游戏状态；实际方向操作核对响应 |
| 原作减速 | 原生等待深度、减速计数和慢速段的推进次数不变 | 对齐逻辑帧与减速计数；未适配的路径使用已经验证的策略，不提前清零倒计时 |
| 绘图与资源 | 读取完整的同一批命令／元数据，旧消费者使用期间不复用资源 | 真正的完成确认、所有权检查、完整交换、后段去重；代表场景核对内容和画面 |
| 录像与保存 | 原生格式、输入来源和回放推进规则不变 | 同一旧录像逐逻辑帧对照，另验证一份新录像保存／冷启动回放；不只比较最终分数 |
| 帧节奏 | 原作速度与最后节拍点不变，不产生新的周期性长帧或持续回退 | 同构建短段 A/B；比较帧间隔尾部、错过出帧时机与回退率 |
| 声音与画面 | 同一逻辑事件的声音请求身份、次数、顺序正确，无新增音画错位或积压 | 保留原音频服务和队列配置；将代表性事件与相应画面关联检查 |
| 暂停与切换 | 暂停、恢复、返回和模块卸载均不留下运行中的旧请求 | 请求代际和逐步骤记录；退出先停止新请求，排空后再失效旧模块 |

行为对照以**相同逻辑帧的输入序列**为基准；低延迟模式本来就会改变物理按键赶上哪一帧、画面何时可见，不要求两次按墙钟发键的游玩结果逐像素相同。应先用固定录像隔离逻辑差异，再用实际输入验证延迟收益。

主要工程风险集中在旧输入被提前消费、结果未完成就复用、后段调用重复执行，以及工作线程来不及完成。对应的输入对照、完成交接、去重与有界等待必须先于默认启用。回退用于异常收尾，不作为“1V 已稳定”的替代证明；若出现玩法分歧、音画异常或明显长帧退化，先修复并重验该路径。

## 两个方案共用的缓冲管理

### 完成身份与所有权

每份可发布结果使用以下身份：

`模块代 + 场景代 + 玩法帧号 + 命令批次 + 缓冲地址 + 原交换序号`

生产线程完成命令、写完 sentinel 和本帧后处理、设置下一次等待深度，并捕获原生等待计数基线后，才发布带 release 语义的完成记录。主线程 acquire 取得记录后检查原始状态，调用原生完整交换函数，再核对交换序号恰好加一、published 指向该批次、下一写入区不与正在读取的缓冲重合。

现有 `commands_end` 和等待入口日志用于分析，不直接升级为生产环境的完成栅栏。尤其等待入口在原生计数基线读取之前，若在那里提前发放唤醒计数，可能发生漏唤醒；完成／等待确认点要放在基线已经捕获的位置。

主线程负责交换，工作线程负责生成命令，不让工作线程自行发布。同步只覆盖身份、所有权和交接状态，不持有状态锁执行客体函数、等待 GPU、调用可能回调的游戏代码或等待卸载。

### 调用次数与模块退出

用本轮的一次性记录分别说明输入构建、辅助输入处理、倒计时推进、render-call 计数和交换哪些已经执行。只跳过确实已完成的对应原调用，不用一个全局“本轮优化成功”布尔量跳过整段。

所有调用保存并恢复当前客体寄存器、栈和浮点环境；通过当前模块身份解析入口。切换／卸载先停止接收新工作，再排空正在执行的调用，最后失效该模块代的记录。不能在 DLL 卸载回调持有装载器锁时阻塞等待，也不能仅凭相同虚拟地址认定仍是原模块。

原始命令解析结束与下游资源引用解除是两件事。实施前必须核对命令正文、关联图形数据的实际消费者及释放边界，并沿用原生状态／资源保护。若某类元数据仍被异步使用，保留其原有租期；不能把 Present 返回当作 GPU 资源已释放。

## 方案 A：2V 稳定路径

### 实施顺序

1. 保持现有输入采样、renderer 输入转换、掩码构建和玩法工作线程的唤醒顺序。
2. 在模块本轮开始读取整套 published 元数据之前，检查上一轮的完成记录。优先位置为两模块的 `8803125C`：原有开始绘图／准备调用已经返回，第一项发布元数据还没有读取。
3. 仅在当前原生倒计时已到应交换的那一轮、工作线程仍在对应等待、缓冲已完成且旧消费者允许复用时，调用原生 `88033070`。不等待工作线程赶工。
4. 验证交换后，让本轮原有 renderer 正常读取这一份新结果。
5. 后段回调的原交换调用由匹配的一次性记录替代，提供其已成功的返回结果；原输入构建、辅助处理、倒计时清零和 render-call 增量仍按原位置执行。下一帧玩法仍在原来的位置醒来。
6. 最后的原生 VBlank 等待、绘图队列和 Present 路径保持原顺序。

这个方案只提前兑现已经完成的交换，消除“新缓冲发布时，本轮已经取过旧缓冲”的整帧等待。不需要新的输入映射，也不在关键路径增加等待新结果的开销。

### 条件不满足时

提前交换前，任何身份、完成、资源或场景条件不满足，就执行原路径；日志记录原因。成功交换后，必须把对应的后段交换记账收完，不能因为随后出现暂停／场景变化就清掉记录、再交换一次。

countdown 大于 1 时保留原作减速过程，不提前让它归零；到原本应交换的那轮才适用提前发布。深度 0、特殊步进或尚未识别的等待入口先走原路径。

### 可行性判断

**较高，作为先实现的兼容保底。** 既有样本的命令在计划取用时早已完成；不移动输入消费和玩法唤醒，主要风险集中在缓冲复用及交换去重，影响面可控制在本游戏适配层。最终发布默认按 1V 的验收结果决定，不要求永久默认 2V。

两帧是正常游玩的验收目标，不是靠经常回退到 original 达成“稳定”。若持续出现回退，须定位并修正门控或生命周期；不能以不崩溃代替两帧保底验收。

## 方案 B：1V 低延迟路径

本方案采用上述虫姬二式“完成后再绘制”的交接结构，改动范围包含输入准备和玩法线程唤醒。它保留 2V 方案的完整缓冲保护及最终原生帧等待，不把最后的出帧等待搬到提交之后。

### 输入必须在玩法前准备好

low 在原始 `UpdateInputs` 完成之后、当前玩法帧开始之前，取得本轮冻结的输入快照。现有主循环的原始输入更新在 `8217E9C8` 前完成；正式提交提前请求前再检查玩法控制器、暂停／转换、模块和场景状态。

当前实现直接复用本体原生输入转换前段，避免维护另一份 action 映射。原生前段提前执行一次、原生后段在正常位置执行，仍须保持合集的键盘／SDL 合并输入和原游戏 action／玩家映射规则：

- 保留两个玩家槽、游戏内按钮映射、模拟方向阈值、特殊控制位和原有短按处理。
- 优先从已经更新的原生 action 状态构建快照，不新增第二套直接读取设备、绕过 config.ini 的路径。
- 验证新转换与原 renderer 的输入端口／玩法掩码逐字段一致。不能只验证四个方向。
- 原生边沿、连发、调试切换和辅助处理每轮只推进一次；为早段消费提供数据，不重复调用整套输入状态更新。
- 录像播放使用录像提供的该逻辑帧输入，live 设备快照不覆盖它；识别不了的状态先使用 balanced。

输入转换用隔离原生前段对独立 oracle 做对照，提前／正常栈位置也使用相同 action 快照比较；实际短按／失焦与录像输入还需实战检查。单独增加一次 XInput 查询不能解决当前已确认的显示排队问题。

### 本轮生成并取用

1. 使用 A 的完成记录和原生交换方式建立正确的初始写入区。启动 low 时可能缩短旧画面的排队，但不跳过逻辑更新、录像输入或减速计数；首轮缓冲整理单独记录，不作为稳态延迟样本。
2. 在主线程进入模块绘图／资源准备之前，确认本轮输入快照和对应的游戏等待均就绪。优先提交点为已核对的状态 13 分支 `8211F0DC`，保留原流程中的状态判断。
3. 提前执行本轮必须的输入辅助步骤、倒计时推进和一次 render-call 增量，唤醒原来的工作线程。先完整发布请求身份，再发放原生唤醒条件。
4. 若仍处于原作减速的中间轮，只推进原来这一轮的计数并呈现既有画面，不额外更新玩法。
5. 真正到期的更新，使用带谓词、请求号和模块代的有界等待接收完成记录；完成后调用原生交换，随后整个原 renderer 从头读取一致的新元数据。
6. 后段回调按步骤去重，保留未移动的音频／外围服务。最终原生帧等待照常执行。

等待在取得绘图资源／队列锁之前完成。不要在 renderer 已读取部分元数据、持有绘图上下文的中间位置等待工作线程，然后临时换一个指针；那会引入锁依赖和新旧元数据混用。

### 截止时间和回退

新增等待用于等待本轮工作完成，不等待“再过一帧”。先以约 2 ms 作为开发候选上限，并按本轮剩余节拍余量收紧；最终预算由实测的完整唤醒至完成耗时和后续绘图预算决定，不直接照搬上游 8 ms。

SDK 已增加 `GuestVblankDeadlineMicros()` 只读快照，复用现有视频节拍时钟。启动、追赶和停止时返回 0，不另建线程，不改变原有等待、计数或中断逻辑。当前开发预算上限 2 ms，并预留 4 ms 给后续绘图；最终取值仍以实际等待尾部和出帧结果验收。

超时分两类处理：

- **还没唤醒工作线程：** 本轮直接使用 balanced，正常晚段调用继续执行。
- **工作已经开始：** 进入 draining，保留该请求的缓冲所有权和已执行步骤记录。本轮使用仍有效的上一份完整画面；工作线程完成后仅交还原请求，下一安全边界恢复 balanced。不能取消一个实际还在运行的写入者，也不能补发第二次逻辑更新。

资源加载另有一种原生行为：同一逻辑更新尚未生成完整命令时，会在资源重试循环中等待后续原生帧推进。不能一边等待整帧完成，一边禁止这些推进，否则两边互相等待。两模块的已核对调用者分别为 `8806F384`／`8806FDBC`；仅实际逻辑线程、匹配模块代和唤醒基线的中途等待才接受。它先结束本次限时等待或 draining，保留已执行输入／驱动步骤的后段记录。后续安全边界可以提前恢复**同一次**尚未完成的逻辑更新，完成身份必须仍是原逻辑号，不发布半成品，也不启动第二次更新。此处等待的是独立唤醒计数；原生绘图倒计时已经被上一成功交换清零，不能错误地要求它等于资源等待深度。机制测试覆盖连续资源重试、超时后恢复和前后步骤恰好执行一次。

### 保留减速公式的原始绘图输入

CA022100 的原生减速公式消费绘图面积统计，不是宿主 CPU 耗时。更早绘图会改变这份统计的逻辑年龄；固定取“前两次逻辑更新”也不成立，因为资源等待会增加视频周期，暂停又可能保持唤醒计数不变。

`RenderMetrics` 按完成时捕获的原生唤醒基线与深度，记下原路径应在何时发布该结果（`baseline + depth - 1`）。每个视频帧只推进一次原始取用模型：当轮晚段发布的结果不能提前算入当轮原始绘图；已经取用过的结果在保持画面的轮次不再产生统计。真实统计只在命令解析器通过空指针／ready 位检查后记录，单纯给 renderer 设置缓冲指针不算解析。缺少本应解析的结果会留下明确异常，不能用猜测的零值代替。

该适配只改变原生公式读取的两个统计操作数，保留其浮点计算、阈值、零统计衰减和最终等待深度选择。1V 的深度大于 1 的完整结果也可以立即绘制，但后段交换记录必须等原来应到期的唤醒计数结清；不提前推进下一次玩法更新。候选实现仍须通过相同录像的统计操作数、等待深度和命令逐帧对照，不能仅由模型测试验收。

持续超时触发的降档保持到本次游戏进程结束，不自动重试 low，避免在一帧／两帧之间反复抖动；若只是因未适配场景暂用 balanced，才在明确的新场景边界重新评估。用户选择的配置不因运行时回退而改写，配置变更在下次启动生效。若检测到所有权本身矛盾，停止提前路径并保留诊断，不继续猜测哪个缓冲可用。

### 可行性判断

**有实现基础，值得做，复杂度明显高于 A。** 当前已测的玩法更新和命令生成不足 1 ms，最终原生等待之前有明显余量；因此没必要通过取消帧节拍或加速游戏争取一帧。

能否稳定达到一帧，取决于三个条件：本轮新输入确实赶上本轮逻辑；工作线程及时交回完整结果；减速／录像／暂停和失败回退保持正确。已有数据支持前进，但尚未测量新同步路径的尾部耗时，也没有覆盖所有减速深度。

推荐先实现正常深度 1 的 low，确认完整输入映射、两模块和录像一致性，再扩展原有减速深度。未支持的减速路径继续用 A；对外描述据实际覆盖决定，不能先承诺所有场景固定一帧。

## 与上游的关系

[SDOJ-Recomp 的说明](https://github.com/eandis/SDOJ-Recomp#input-lag)提供了“临近消费刷新输入＋提前回调／交换、跳过晚段重复调用”的参考。固定审阅版本为 [cc35e038 的实现](https://github.com/eandis/SDOJ-Recomp/blob/cc35e038d4126bc1c359597dcb94e6815477818d/src/lag_patches.h)，其中包括请求身份、模块／场景代、等待深度、超时 draining 和初次缓冲同步。

## 实施与验收顺序

1. **先验证交接基础。** 补齐缓冲正文／元数据的引用寿命，增加真正的完成／等待确认，做身份、swap 序号和旧读者检查；维持 original 行为取得对照。
2. **交付 A。** 只改提前发布和后段交换去重。正常速度链稳定从三 epoch 变两 epoch，输入顺序与原生逻辑更新次数不变。保存这个独立可构建、可回归的兼容基线；最终默认档位按 B 的验收结果确定。
3. **证明 B 的输入等价。** 在原有时序下计算新输入快照，与原端口／玩法掩码比较；覆盖方向、所有动作、映射、短按、失焦、两个玩家槽以及录像输入来源。
4. **加入 B 的提前请求。** 完成请求、限时等待、整套发布、逐步骤去重和 draining；先用无窗口的状态模型筛掉失败路径。
5. **进行小而完整的实战比较。** 使用同一构建的 original／balanced 或 balanced／low 控制，结合固定短录像、存活自机方向输入、两种模块、一次暂停／返回／切换。正常启动的简短无细粒度 trace 片段检查帧节拍和音画连续性，并按“行为保持与验收要求”逐项记录。
6. **开放对应 Frame Delay 档位。** 验证配置缺省、3／2／1 映射、无效值、重启生效，以及日志的请求／实际策略；只开放已经完成目标与正确性验收的档位。

离线状态测试至少覆盖：完成先于等待、通知先于阻塞、假唤醒、请求前放弃、写入中超时、迟到完成、暂停／卸载、缓冲地址复用、交换失败、原生减速深度变化，以及每轮各个移动步骤恰好执行一次。时间预算只决定能否采用新画面，不能决定是否再多跑一次逻辑。

真实回归优先按机制选样本，避免每个模式都重打：

- CA022110 的 Xbox360／Shot 训练复用已有场景，核对新输入到真实变化命令及对应输出。
- CA022100 选一条短的 Arcade HD 或 Ver.1.5 场景，补另一布局与一次实际减速片段。
- 同一旧录像在控制路径和优化路径中按**逻辑帧**比较输入、可核对的游戏状态／分数、命令内容和减速计数；跳过地址、墙钟等无语义差异，不只看最终分数。
- 短的新录像保存后，按逻辑帧核对回放。无需重做社区上传或其余四游戏的完整验收。

| 验收项 | balanced | low |
| --- | --- | --- |
| 正常速度同一输入结果的链 | copy→source 跨一轮；copy→输出两 epoch | 当前输入→copy→source 在本轮；copy→输出一 epoch |
| 输入新鲜度 | 原顺序不变，验证真实键沿 | 原始快照身份、转换、消费及输出一致，不能沿用旧缓存冒充 |
| 帧节拍 | 保留原生等待，无新增周期性长帧 | 额外工作在原等待预算内完成；报告截止未赶上及回退次数 |
| 正确性 | 无重复交换、写读重叠、帧计数变化 | 另要求无重复／跳过逻辑更新、重复输入边沿或录像分歧 |
| 音画一致性 | 原事件声音请求不变，提前画面后无新增错位 | 提前更新不重复推进音频服务，不引入积压或事件错配 |
| 失败收尾 | 保持正常原路径或收完已完成交换 | 已开始的工作必须排空，再恢复 A |

验收记录同时保留命中率、回退原因、最差帧和同场景对照。CPU 时钟、系统优先级、帧率上限和最终 VBlank 等待不作为这次的优化手段。

## 自审后的结论

A／2V 的收益来源单一，现有样本已证明它有足够早完成的输入结果，适合先做稳定保底。B／1V 参考虫姬二的完整交接逻辑，计算预算有希望，但必须把输入新鲜度、完成身份与资源所有权一起处理。“激进”仅指改动范围更大，不代表降低正确性要求。

实施上保留 A 的独立版本和 2V 选择项，B 出现问题可回到已经验收的两帧路径。先把 2V 做实，再以同一输入到对应输出的真实链路确认 1V 收益，同时通过玩法、减速、录像、音画与帧节奏对照。本项止于 1V，0V 留在范围之外。

本次补充审查记录位于本地 `.local/analysis/sdoj-latency-design-audit-r2.json`，生成脚本为同目录的 `sdoj-latency-design-audit-r1.py`（输出路径参数指定 r2）。它核对原报告／日志哈希、可观测提前发布条件、两模块输入虚表和写入状态语义；不是优化后的性能结果。
