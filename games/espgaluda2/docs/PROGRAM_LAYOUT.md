# 游戏程序与静态分析

本项目支持的八个 XEX 由 config/game-inputs.json 固定。以下地址与结果仅适用于这些哈希。default.xex 常驻，七个 dat 模块共享 0x88000000 映像区；实际代码段从 0x88020000 开始。模式切换必须卸载旧模块，再装载新模块。

## 生成与接口盘点

default.xex 映像为 10 MiB，代码段为 0x82090000 至 0x8237BDDC（不含末地址）。主程序有 174 项系统导入，每个 overlay 有 40 项；导出解析器均能找到名称。解析器标签并非函数实现状态的完整依据，最终还需编译链接和调用行为验收。

八模块均通过生成器 Register、Scan、Discover、GapFill、Merge、Validate 阶段，未使用 --force。主程序额外入口在 recomp/default-functions.toml，包含直接跳转目标，以及静态核对的地址引用回调、尾调用跳板和排序比较函数，不修改原指令。启动时漏掉的 0x822A8448 是由 0x822C1748 构造并传给排序例程的比较函数，完整范围至 0x822A84D0；它没有常见的栈入口。另有二十个地址引用短回调按实际指令边界声明，避免依赖运行到相应回调后才逐项发现。

生成使用 scripts/Generate.ps1，逐次处理 default 和一个 overlay，避免共享地址互相覆盖。生成后的七项注册表只合并模块元数据；游戏函数正文完全来自本地输入。generated/generation.json 记录工具、SDK、声明、输入与全部 129 个生成文件哈希。中途失败不会留下有效的完成收据。

## 主程序的模块选择

主程序在 0x820BB124 读取对象偏移 0x960 的内部选择值，在 0x820BB154 至 0x820BB1A4 选择路径并调用装载包装函数。静态分支对应如下，菜单模式名称另行验证：

| 内部选择值 | XEX | 路径地址 | 选择分支地址 |
| --- | --- | --- | --- |
| 0 | dat00.xex，Arcade 已实测 | 0x82009458 | 0x820BB154 |
| 1 | dat12.xex，Xbox 360 已实测 | 0x82009438 | 0x820BB16C |
| 2 | dat11.xex，Arrange 已实测 | 0x82009448 | 0x820BB160 |
| 3 及超出范围的默认值 | dat15.xex，Black Label 已实测 | 0x820093EC | 0x820BB19C |
| 4 | dat164.xex，Black Label Novice 已实测 | 0x820093FC | 0x820BB190 |
| 5 | dat163.xex，Xbox 360 Novice 已实测 | 0x82009410 | 0x820BB184 |
| 6 | dat162.xex | 0x82009424 | 0x820BB178 |

装载包装函数为 0x820DD638，调用主程序 0x8237B78C 的 XexLoadImage thunk；GetProcedureAddress 包装函数为 0x820DD5F8，对应 0x8237B65C。装载后先查询 ordinal 1，再查询 ordinal 2，并调用 ordinal 2 返回的函数创建模块对象。游戏的卸载导入 thunk 为 0x8237B77C，后续 hook 必须从本作实际调用点建立，不能照搬虫姬二。

## 内存所有权检查

SDK 已修正 XEX 装载时重置整个共享堆的问题，保留主程序与其他 live image 的分配记录。reserve+commit 现在也拒绝已占用范围；失败或密钥重试只释放当前装载尝试拥有的内存，不能释放或覆盖其他模块。

静态检查对七个 overlay 各执行三次无 DllMain 的装载、卸载、重装载，核对主程序分配不变、旧 overlay 释放及地址可重新使用；还尝试在 live overlay 范围装载另一个模块，确认被拒绝且原代码样本和分配记录不变。独立自制分配测试覆盖组合 reserve+commit、部分重叠、释放与重用。这些检查不涉及游戏线程、GPU 或 SDL 输入。

部分 overlay 的 PE 头仍列出 XEX 已剥离的 .edata/.reloc 等尾部元数据。分析报告保留其段头，但不读取或导出映像范围之外的字节；可执行段越界则直接失败。


批量检查数据段引用、但尚未注册的短回调：

```powershell
py -3.12 scripts/callback_inventory.py .local/analysis/<本次目录> --output .local/callback-review-new.json
```

该工具校验 XEX 和段副本哈希，只输出候选，不自动改声明。数据段也有异常展开与清理入口，因此候选不能直接当作虚表。按引用上下文、寄存器调整与控制流核对后写入 default-functions.toml；其中 0x82116AC8 是已确认的虚表转发入口，用于模块释放后的清理路径。尾随的异常处理入口不按普通回调批量注册。

## 原生社区流程

联网接入沿用虫姬二的边界：保留游戏的成绩资格判断、提示、录像录制和播放，仅替换系统通信接口。共用后台 HTTP、异步完成与取消机制，不把虫姬二的地址、榜单列或录像时序直接套到 G2。

以下结论来自受支持 default.xex 的静态控制流及原生提示文本。还需由接入后的实际菜单、成绩和录像流程验证，不是联网实测通过记录。

### 成绩与录像的顺序

原生任务从 0x820AA770 分发，主要过程为：

```text
整理本局记录 → 读取本人旧成绩 → 预估排名 → 筛选个人新高
  → 符合录像条件时询问玩家 → 分批提交成绩并 Flush
  → 玩家同意时上传对应录像 → 结束会话
```

- 0x820A7748 从两个玩家的记录整理成绩；没有有效记录时不启动提交任务。
- 0x820A7DA0 读取本人已有成绩，0x820A7EA0 将返回的 rating 放入候选记录。0x820A8100 仅保留旧成绩严格小于本局成绩的榜单，同分不算提升。初始候选记录为零值。另一个本人排名读取函数 0x820A9700 在有 view 时直接读取首行，因此指定用户的统计查询必须和虫姬二一样，为未上榜用户提供本地 rank 0／零值统计行；该行不插入服务器或公开榜单。
- 0x820A7F90 发起排名预估。0x820A8088 将预估名次不大于 10 的记录标为录像候选，并排除合并两名玩家成绩的情况。该判断不应改成所有成绩都附带录像。
- 状态 7 统计录像候选；有候选且本局录像缓冲有效时显示确认框。确认或拒绝都继续提交成绩，拒绝只关闭随后的录像上传。原生提示明确说明录像在成绩登记之后上传。
- 状态 12 调用 0x820A8840，以每批最多五个 view 提交成绩；状态 13 等待 Flush，并处理后续批次。状态 14 结束计分会话步骤后，状态 15 才按候选 view 构建路径并上传录像。
- 异步失败转入状态 33，由 0x820A9D38 结束会话、释放资源并回到空闲；不能用统一返回成功掩盖失败。路径构建失败有一次短等待后重试，这不是跨进程离线补传。

虫姬二维护源码的原生路径先上传录像，再提交成绩，因此它需要暂存未绑定的录像。G2 应先保存服务端确认的本次成绩引用，再接受这次任务的录像；失败的新局不能绑定到上一局的成绩。两款游戏共用传输机制，关联顺序分别适配。

持久化待传、后台重试与重启补传是虫姬二 PC 移植层已有的增强机制。G2 这条原生任务路径尚无跨重启补传的证据，先完成原生榜单、成绩和录像，再按同样的公共机制添加增强项；不改原版的上传资格或玩家确认。

### 数据与系统边界

0x820066B8 的表有 84 个唯一 view，覆盖内部模式码 20–26、三个分类码及“全部／三个角色”四种角色筛选。内部模式码和分类码暂保留数值；不能据此宣称有七个 PLAY 模式，也不猜测分类是周榜、月榜或难度。提交时使用游戏实际选择的 view。

成绩写入含 17 个属性。总分来自 0x20000001，类型为 64 位整数；0x20000002–0x20000007 是另外六个 64 位成绩字段。写入构建函数 0x820A79F0 与榜单解析的 0x820A8C74–0x820A8DB8 对应如下；读取列不是属性 ID 的低 16 位直拷贝。

| 写入属性 | 读取位置 | 类型与用途 |
| --- | --- | --- |
| 0x20000001 | 行 rating | 64 位总分 |
| 0x20000002–0x20000007 | 列 1–6 | 六个 64 位分项 |
| 0x10000008 | 列 7 | 32 位角色值 |
| 0x1000000C | 列 8 | 零起始关卡值，原生 UI 显示时加一 |
| 0x10000010、0x1000000A | 列 9、10 | 原生整数元数据 |
| 0x1000000F、0x10000009、0x1000000B | 列 11、12、13 | 原生整数元数据；列 12 为 Continue |
| 0x1000000D | 列 14 | 原生姓名字节 |
| 0x20000011 | 列 15 | 64 位 UTC FILETIME，不能转成浮点或提前加时差 |

读取列 0xFFFA 写到行尾的附加元数据，提供该行已确认附件的字节数。尚未上传或未关联附件时置零，不把原始 0x10008011 直接当作可下载附件，也不沿用虫姬二的列 1／列 8 录像约定。

录像显示经 0x820DD090 执行 UTC 到本地时间转换，再由 0x820DD008 拆分日期字段；前者通过 XConfig 读取时区。Windows 宿主在该接口提供系统的分钟偏差、标准／夏令时偏差及四字节切换规则，系统 FILETIME 和存储内容保持 UTC。不把显示修复放入 KeQuerySystemTime 或 RtlTimeToTimeFields 等全局时钟／纯转换函数。

| 边界 | G2 地址 | 接入职责 |
| --- | --- | --- |
| 指定用户统计／榜单枚举 | 0x820DC5F0／0x820DC6C8 | 使用 SDK 的 CommunityService 统计通路 |
| 成绩写入 | 0x820D9F20 | XGI 消息 0xB0025，保留原生异步完成语义 |
| 排名预估 | 0x820D9688 | 仅替换静态链接的系统 API 边界，供原游戏判断资格 |
| 本机／远端录像路径 | 0x820D9FE0／0x820DA078 | 不透明游戏命名空间，不接受任意路径或 URL |
| 录像上传／下载 | 0x820D91B8／0x820D8ED8 | 保留原始数据，另行确认 G2 网络容器、容量与版本 |

核对元数据与边界哈希：

```powershell
py -3.12 scripts/analyze_community.py .local/analysis/<本次目录> --output .local/community-census-new.json
```

工具先核对 default.xex、分析收据和段副本哈希，只输出 view 元数据、函数边界及摘要，不执行游戏，不复制程序正文，不改配置或服务。语义结论来自上述人工控制流核对，不把元数据扫描当作动态验证。原始段、提示文本和报告留在本地忽略目录。

### 录像传输与关联

G2 适配使用 `espgaluda2-replay/<view>/<owner>` 命名空间；SDK 默认的虫姬二命名空间保持不变。系统边界只构造受控的不透明路径，不使用游戏传入的名字创建宿主文件或访问任意 URL。

每次原生成绩批次取得服务端确认后，适配保留本局各 view 的成绩引用。相同分数、角色和 UTC 时间的后续批次可继续登记；新局或写入失败会清理旧引用，避免把录像接到上一局。下载使用榜单中该条成绩明确关联的录像引用，不按昵称猜测“最新录像”。

`src/community/replay_format` 负责 G2 独立的版本 2 包络：104 字节头、原始压缩数据和偏移 96 的载荷长度。首字段是本地保存校验值，不是文件长度；原生网络上传时可以为零，稍后的 0x8209D640 本地保存路径才计算并填入。不将本地文件的非零值当成网络格式要求，也不套用虫姬二的格式。包络中的分数、角色与 UTC 时间，以及原生成绩的附件字节数，须与待关联成绩一致。压缩内容保持原样，服务器不执行或解压游戏输入，传输完整性另以 SHA-256 核对。

服务端 `/scores`、`/replays` 与 `/leaderboard` 分别处理成绩、附件和榜单；附件按 SHA-256 去重，同一成绩的重复上传幂等，内容冲突则拒绝。C++ 和 Python 自造数据测试覆盖跨批次关联、错误局拒绝、未分享附件隐藏、远端玩家下载及字节校验；实际游戏内验收单独记录在 TEST_MATRIX.md。
